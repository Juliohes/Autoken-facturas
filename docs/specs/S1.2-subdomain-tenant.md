# Spec: S1.2 Resolución subdominio → tenant

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Aprobada por Julio antes de escribir tests.

- **ID / tarea:** S1.2
- **Contexto (módulo):** `tenancy` (+ `shared` para el middleware y la sesión de BD)
- **ADR relacionados:** ADR-0001 (RLS de dos niveles), ADR-0004 (subdominios de primer nivel). Cierra
  el issue **#48** (lookup slug→tenant pre-contexto) y la parte de lifespan del **#50**.
- **Estado:** aprobada por Julio (2026-07-07)

## 1. Problema y valor de dominio

Cada asesoría vive en su subdominio (`<slug>.autoken.es`). Antes de atender cualquier petición hay
que saber **de qué tenant es**, para (a) fijar el contexto de aislamiento (`app.tenant_id`) y (b)
pintar el branding correcto en el login público. La dificultad: esa resolución ocurre **antes** de
tener contexto de tenant, y la RLS de `tenants` (aislada por su propio `id`, S1.1) tapa el `SELECT`
por slug desde el rol runtime. S1.2 resuelve el subdominio a tenant por un **único camino acotado**
(una función `SECURITY DEFINER`), sin abrir un agujero de lectura sobre `tenants`.

## 2. Lenguaje ubicuo

- **Subdominio / slug**: la etiqueta de primer nivel del host (`ilex` en `ilex.autoken.es`). Único
  por tenant (S1.1: `tenants.slug`).
- **Dominio base**: `autoken.es` en producción; en desarrollo/tests también `localhost` (p. ej.
  `ilex.localhost`). Configurable (`base_domain`).
- **Host reservado / no-tenant**: el dominio raíz (`autoken.es`, `www.autoken.es`) y los subdominios
  de plataforma (`panel`, `panel-staging`), que **no** son asesorías. No resuelven a tenant.
- **`resolve_tenant(slug)`**: función SQL `SECURITY DEFINER` que devuelve los datos **públicos** del
  tenant **activo** con ese slug (id, slug, name, is_demo), saltando la RLS de forma controlada. Es
  el ÚNICO camino por el que el rol runtime obtiene un tenant por slug.
- **Contexto de tenant de la petición**: `request.state.tenant` (los datos públicos resueltos) o
  `None` si el host es no-tenant.
- **404 neutro**: respuesta 404 genérica, idéntica para "subdominio inexistente" y "tenant
  suspendido"; no revela si un tenant existe.

## 3. Comportamientos (criterios de aceptación)

> Observable vía HTTP (cliente ASGI con cabecera `Host`) contra un Postgres real con el esquema de
> S1.1 y un tenant sembrado. Endpoint testigo: `GET /api/v1/tenants/current`.

### C1 — Un subdominio de tenant activo resuelve al tenant
- **Given** existe el tenant activo `ilex` (I-Lex).
- **When** llega una petición con `Host: ilex.autoken.es` (o `ilex.localhost`) a `/api/v1/tenants/current`.
- **Then** responde 200 con los datos públicos del tenant (al menos `slug = "ilex"` y su `name`).

### C2 — Un subdominio inexistente da 404 neutro
- **Given** no existe ningún tenant con slug `nope`.
- **When** llega `Host: nope.autoken.es`.
- **Then** responde **404** con cuerpo genérico (sin pistas de si el tenant existe o no).

### C3 — Un tenant suspendido da 404 neutro (no se distingue de inexistente)
- **Given** existe el tenant `viejo` con `status = 'suspended'`.
- **When** llega `Host: viejo.autoken.es`.
- **Then** responde **404** neutro, **idéntico** al de C2 (mismo status y cuerpo).

### C4 — Los hosts no-tenant no resuelven tenant (y no son 404 por sí mismos)
- **Given** los hosts del dominio raíz (`autoken.es`, `www.autoken.es`) y de plataforma (`panel.autoken.es`).
- **When** llega una petición con esos hosts.
- **Then** `request.state.tenant` es `None`; la petición sigue su curso normal para rutas públicas
  o de plataforma (no se fuerza 404 por el host). `GET /api/v1/tenants/current` en ese caso da 404
  (no hay tenant), pero p. ej. `/api/v1/health` responde 200.

### C5 — El puerto del Host se ignora al extraer el subdominio
- **Given** el tenant `ilex`.
- **When** llega `Host: ilex.localhost:8000`.
- **Then** resuelve igual que sin puerto (200, `slug = "ilex"`).

### C6 — `resolve_tenant` es el único camino: el SELECT directo sigue tapado por RLS
- **Given** el rol runtime `autoken_app` sin `app.tenant_id` fijado.
- **When** ejecuta `SELECT * FROM resolve_tenant('ilex')` y, aparte, `SELECT * FROM tenants WHERE slug='ilex'`.
- **Then** la **función** devuelve la fila del tenant; el **SELECT directo** devuelve **0 filas** (la
  RLS de S1.1 sigue intacta). La función no filtra existencia por otra vía.

### C7 — `resolve_tenant` solo devuelve tenants activos
- **Given** un tenant `suspended`.
- **When** el rol runtime ejecuta `resolve_tenant(<slug suspendido>)`.
- **Then** devuelve **0 filas** (la función filtra por `status = 'active'`).

## 4. Invariantes y reglas de negocio

- **Anti-cruce de tenants**: la resolución no abre ninguna lectura de `tenants` fuera de la función
  acotada; el aislamiento de S1.1 (0 filas sin contexto) se mantiene intacto (C6).
- **No enumeración**: subdominio inexistente y tenant suspendido son indistinguibles desde fuera (C2 = C3).
- **`resolve_tenant`**: `SECURITY DEFINER`, propietaria = un rol que salta la RLS (superusuario en
  test/CI; en prod, el rol owner con BYPASSRLS, ver #50), `SET search_path = public` (anti-inyección),
  `REVOKE ALL FROM PUBLIC` + `GRANT EXECUTE TO autoken_app`. Devuelve solo campos públicos, nunca
  secretos.
- La extracción del subdominio es case-insensitive y tolera el puerto.

## 5. Casos límite y errores

- Host ausente o vacío → tratado como no-tenant (sin 404 por sí mismo).
- Host que no termina en el dominio base (p. ej. una IP, o el `custom_domain` de Setex) → **fuera de
  alcance** aquí (el `custom_domain` se resolverá cuando se aborde el tenant Setex); de momento,
  no-tenant.
- Subdominio con varias etiquetas (`a.b.autoken.es`) → se toma la etiqueta de primer nivel más a la
  izquierda como slug; si no resuelve, 404 neutro (coherente con C2).
- La conexión a BD falla al resolver → error 500 controlado (no 404: no se debe enmascarar un fallo
  de infraestructura como "tenant inexistente").

## 6. Fuera de alcance (no-objetivos)

- Login, JWT y la comprobación `tenant_id del JWT == subdominio` (S1.3).
- Fijar `app.tenant_id` en la sesión de BD por petición para las rutas de negocio: el mecanismo
  (`tenant_session`) ya existe (S1.1); su **cableado como dependencia por petición** se hará cuando
  haya endpoints de negocio (S1.3+). Aquí basta con dejar `request.state.tenant` disponible.
- RBAC por rol (S1.6), branding/theming en el frontend, `custom_domain` de Setex.
- Alta/gestión de tenants (plataforma).

## 7. Notas de verificación (cómo se prueba de extremo a extremo)

- Tests con **Postgres real** (esquema S1.1 + migración de `resolve_tenant`) y cliente ASGI (httpx)
  fijando la cabecera `Host`. Se siembra un tenant activo (`ilex`) y uno suspendido con el rol
  superusuario; la app se conecta como rol runtime.
- Endpoint testigo `GET /api/v1/tenants/current`: 200 con datos públicos del tenant resuelto, 404
  neutro si no hay tenant. `GET /api/v1/health` sirve para C4 (host no-tenant sigue respondiendo).
- Se añade la integración del engine en el **lifespan** de FastAPI (`dispose_engine` al cerrar,
  parte de #50) para no dejar el pool colgado.
- Datos de dominio: tenant demo real `ilex` (DNS `ilex.autoken.es` ya creado, 2026-07-07).
