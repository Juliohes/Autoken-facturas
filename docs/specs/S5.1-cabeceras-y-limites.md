# Spec: S5.1 Cabeceras y límites

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Aprobada por Julio antes de escribir tests.

- **ID / tarea:** S5.1
- **Contexto (módulo):** shared (cabeceras, rate-limit genérico), identity (aplicación a `/activate/confirm` y `/refresh`)
- **ADR relacionados:** ninguno nuevo; se apoya en el diseño ya existente de `identity/ratelimit.py` (S1.3/S1.4)
- **Estado:** aprobada por Julio (autoaprobación autorizada para el Sprint 5, ver memoria de sesión)

## 1. Problema y valor de dominio
Antes de dar el salto a producción, la API necesita cerrar dos frentes de "hardening" básico:

1. **Cabeceras de seguridad**: ya existen desde S1.6 (`shared/security_headers.py`), pero nunca se han
   revisado contra el checklist real de Mozilla Observatory ni se han completado con las cabeceras
   modernas de aislamiento entre orígenes (COOP/CORP), que son gratis de añadir en una API que no sirve
   HTML ni recursos embebibles.
2. **Límites de tasa (rate limiting)**: el login (S1.3) y el registro público (S1.4) ya están protegidos
   contra fuerza bruta. Pero al revisar el resto de endpoints no autenticados se ha encontrado un hueco
   real: `POST /auth/activate/confirm` valida un código TOTP de 6 dígitos **sin ningún límite de
   intentos**. Quien intercepte o adivine el token de activación (256 bits, difícil pero no imposible de
   filtrar por otras vías: email interceptado, log, etc.) podría entonces probar los ~1.000.000 de
   códigos TOTP posibles sin que nada se lo impida, y enrolar su propio segundo factor antes que el
   usuario legítimo, secuestrando la cuenta. `POST /auth/refresh` tampoco tiene ningún límite: aceptar
   cualquier volumen de intentos de rotación de un token robado/adivinado facilita tanto el abuso como
   una carga innecesaria sobre Redis.

## 2. Lenguaje ubicuo
- **Endpoint sensible**: endpoint alcanzable SIN autenticación previa cuyo abuso (fuerza bruta, spam,
  carga) tiene impacto real de seguridad o de coste. En esta tarea: `/auth/activate/confirm` y
  `/auth/refresh`. (`/auth/login` y `/auth/register` ya están cubiertos desde S1.3/S1.4; no se tocan
  aquí salvo para reutilizar su mismo mecanismo).
- **Ventana deslizante (rate-limit)**: contador en Redis con TTL que cuenta intentos en los últimos N
  segundos; superado el tope, el intento siguiente responde `429` hasta que la ventana expira (mismo
  concepto ya implementado en `identity/ratelimit.py` para login/registro).
- **Cabecera de aislamiento de origen (COOP/CORP)**: `Cross-Origin-Opener-Policy` /
  `Cross-Origin-Resource-Policy`, impiden que otro origen abra esta API como ventana emergente
  relacionada o incruste sus respuestas, mitigación de clase Spectre/XS-Leaks.

## 3. Comportamientos (criterios de aceptación)

### C1 — Las cabeceras de seguridad ya existentes se mantienen intactas
- **Given** cualquier respuesta de la API (autenticada o no, éxito o error)
- **When** se inspeccionan sus cabeceras
- **Then** siguen presentes `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`
  (y `Strict-Transport-Security` solo en producción) — regresión, no se retira nada de S1.6.

### C2 — Nuevas cabeceras de aislamiento de origen en toda respuesta
- **Given** cualquier respuesta de la API
- **When** se inspeccionan sus cabeceras
- **Then** incluye `Cross-Origin-Opener-Policy: same-origin` y `Cross-Origin-Resource-Policy: same-origin`
  (una API JSON que no necesita ser embebida ni abierta como ventana relacionada desde otro origen).

### C3 — Confirmar activación con TOTP: límite de intentos por token
- **Given** un token de activación válido con su secreto TOTP pendiente de confirmar
- **When** se envían códigos TOTP incorrectos repetidamente contra `POST /auth/activate/confirm` con
  ese mismo token, hasta superar el tope configurado en la ventana
- **Then** el intento que supera el tope responde `429`, sin validar ya el código (aunque por
  casualidad fuera el correcto); el mensaje no distingue "token inválido" de "límite superado" a
  quien no lo alcanzó (mismo criterio anti-enumeración que login), pero el `429` en sí es visible
  (necesario para que el cliente sepa que debe esperar, igual que hace login).

### C4 — Confirmar activación: un código correcto dentro del tope funciona con normalidad
- **Given** un token de activación válido, con menos intentos fallidos que el tope
- **When** se envía el código TOTP correcto
- **Then** la cuenta queda activada con normalidad (sin cambios de comportamiento respecto a hoy).

### C5 — El límite de activación es por token, no global
- **Given** dos tokens de activación distintos (de dos usuarios distintos)
- **When** uno de ellos agota su tope de intentos
- **Then** el otro token puede seguir intentando con normalidad (el límite no bloquea a todos los
  usuarios en proceso de activación por el fallo de uno solo).

### C6 — Pasada la ventana, se vuelve a permitir
- **Given** un token de activación que agotó su tope de intentos
- **When** transcurre la ventana temporal completa
- **Then** un nuevo intento de código TOTP contra ese token se evalúa con normalidad (ni bloqueado
  para siempre, mismo criterio que C17/C22 de login).

### C7 — Refrescar el token: límite de intentos por IP
- **Given** una IP que llama a `POST /auth/refresh` repetidamente con tokens inválidos, hasta superar
  el tope configurado en la ventana
- **When** llega el intento que supera el tope
- **Then** responde `429`, sin consultar ya Redis para validar el token.

### C8 — Refrescar el token: un token válido dentro del tope funciona con normalidad
- **Given** una IP por debajo de su tope de intentos
- **When** llama a `/auth/refresh` con una cookie de refresh válida
- **Then** la rotación ocurre con normalidad (sin cambios de comportamiento respecto a hoy).

## 4. Invariantes y reglas de negocio
- Anti-enumeración: un `429` nunca revela si el token/código de por sí habría sido válido.
- Anti-cruce de tenants: el rate-limit de activación/refresh es un mecanismo transversal (por
  IP/token), no depende de RLS ni de contexto de tenant — no hay dato de negocio en juego.
- El mecanismo reutiliza el patrón atómico ya validado de `identity/ratelimit.py`
  (`INCR`+`EXPIRE` en un único script Lua): ninguna clave puede quedar sin TTL y bloquear para
  siempre.
- `/auth/login` y `/auth/register` NO se tocan: ya tienen su propio rate-limit desde S1.3/S1.4 y
  quedan fuera de esta tarea salvo por compartir la misma primitiva de ventana deslizante si se
  extrae a un módulo común.

## 5. Casos límite y errores
- Redis caído: mismo criterio que login (`redis_guard` ya existente en el router) — fallo cerrado,
  `503`, nunca se abre el paso sin poder contar intentos.
- Content-Length/cuerpo malformado en `/activate/confirm` o `/refresh`: los validadores Pydantic ya
  existentes deciden antes de llegar al rate-limit; no cambia.
- Un token de activación ya consumido o caducado sigue devolviendo el mismo `401` neutro de siempre,
  a menos que el propio IP/token ya esté por encima del tope (entonces `429` antes de mirar el token).

## 6. Fuera de alcance (no-objetivos)
- **Informe real de Mozilla Observatory ≥ A**: Observatory escanea una URL pública desplegada; no
  hay ningún despliegue público accesible desde este entorno de trabajo. Se deja documentado en la
  implementación el checklist de cabeceras que Observatory puntúa (todas cubiertas por C1/C2) y el
  escaneo real queda pendiente de una sesión futura con acceso a staging/producción — mismo patrón
  ya usado en S4.6 (Caddy/TLS real) y S2.2 (verificación en móvil real).
- **`Strict-Transport-Security` con `preload`**: añadir `preload` es un compromiso público y difícil
  de revertir (afecta a todos los subdominios presentes y futuros vía la lista de precarga de los
  navegadores) — no se añade sin que Julio lo decida explícitamente cuando el dominio real esté
  operativo.
- **Rate-limit en endpoints ya autenticados** (`POST /uploads`, `POST /companies/import`, acciones de
  `platform_admin`...): quien los alcanza ya tiene una identidad conocida y revocable (no es abuso
  anónimo); si hace falta un tope de consumo por tenant, es un tema de cuotas/coste, no de esta tarea
  de hardening de superficie no autenticada.
- **Rate-limit por CIDR o WAF**: fuera de alcance de la aplicación; sería infraestructura (Caddy/Cloudflare).
- **Cambiar el mecanismo de login/registro**: se reutiliza tal cual, no se toca su comportamiento.

## 7. Notas de verificación (cómo se prueba de extremo a extremo)
- C1/C2: petición HTTP real contra la app de test (cliente `httpx`), inspeccionando cabeceras de la
  respuesta de cualquier endpoint existente (p. ej. `GET /api/v1/health`).
- C3-C6: flujo real de activación (sembrar token con `activation.issue_activation_token` +
  `activate_account`, como ya hacen los tests de S1.3) contra Redis real de test, llamando a
  `POST /auth/activate/confirm` repetidamente con códigos incorrectos hasta el tope, luego uno
  correcto/esperar la ventana.
- C7/C8: flujo real de refresh (login real -> cookie de refresh) contra Redis real, llamando a
  `POST /auth/refresh` repetidamente con una cookie manipulada hasta el tope.
- Igual que el resto del proyecto: Postgres/Redis reales de test, nunca mockeados para el
  comportamiento observable.
