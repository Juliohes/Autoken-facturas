# Spec: S1.1 Núcleo de tenancy + aislamiento por RLS

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Aprobada por Julio antes de escribir tests.

- **ID / tarea:** S1.1
- **Contexto (módulo):** `tenancy` (+ `shared` para la sesión de BD)
- **ADR relacionados:** ADR-0001 (RLS de dos niveles). Posible ADR nuevo sobre la mecánica de
  **doble rol de BD** (owner/migraciones vs runtime) si al implementar surge una decisión no trivial.
- **Estado:** aprobada por Julio (2026-07-07)

## 1. Problema y valor de dominio

Autoken es multi-asesoría. La regla de oro nº 5 exige **aislamiento total**: una asesoría (tenant)
jamás ve datos de otra, y un empleado de una empresa (company) no ve datos de otra empresa del mismo
tenant. Ese aislamiento no puede depender solo de que el código de aplicación "se acuerde" de filtrar:
debe garantizarlo el **motor de base de datos**, de modo que un `WHERE` olvidado no filtre datos entre
asesorías. S1.1 pone los cimientos: el esquema núcleo de tenancy y el mecanismo de aislamiento por RLS
sobre el que se construirá todo el producto.

## 2. Lenguaje ubicuo

- **Plataforma**: el operador (Autoken). Roles `platform_admin` (Julio, Alberto).
- **Tenant** = asesoría. Identificada por `slug` (subdominio). El tenant demo definitivo es **I-Lex**
  (`slug = ilex`).
- **Company** = empresa cliente de una asesoría. Un `user` (empleado/autónomo) ve **solo** su company.
- **Rol owner/migraciones**: rol de BD que crea el esquema y es dueño de las tablas. Corre las
  migraciones. NO lo usa la API en runtime.
- **Rol runtime** (`autoken_app`): rol de BD con el que se conecta la API. **NOSUPERUSER, NOBYPASSRLS**
  y **no es dueño** de las tablas, para que la RLS le aplique sin excepción.
- **Variables de sesión**: `app.tenant_id` y `app.company_id`, fijadas con `SET LOCAL` dentro de la
  transacción de cada petición. `app.company_id` sin fijar (NULL) = contexto de asesoría (ve todo su
  tenant); fijada = contexto de una company concreta (ve solo esa).
- **Tabla de negocio**: toda tabla con datos de un tenant. Lleva `tenant_id`, RLS `FORCE`, e índice
  compuesto que empieza por `tenant_id`. (`cif_lookups`, caché pública global, quedará fuera; no aplica
  en S1.1.)

## 3. Comportamientos (criterios de aceptación)

> Cada escenario = un test. Se ejecutan contra un **PostgreSQL real** conectando como el **rol runtime**.

### C1 — Sin `app.tenant_id` no se ve ninguna fila (el test estrella, §8 del plan)
- **Given** existen filas de dos tenants A y B en una tabla de negocio (p. ej. `companies`).
- **When** el rol runtime consulta la tabla **sin** haber fijado `app.tenant_id`.
- **Then** la consulta devuelve **0 filas** (no error): sin contexto de tenant no hay datos.

### C2 — Un `app.tenant_id` distinto no ve las filas de otro tenant
- **Given** una fila del tenant A.
- **When** el rol runtime fija `app.tenant_id = B` y consulta.
- **Then** devuelve **0 filas**.

### C3 — Con el `app.tenant_id` correcto se ven solo las filas de ese tenant
- **Given** filas de A y de B.
- **When** el rol runtime fija `app.tenant_id = A` (sin `app.company_id`) y consulta.
- **Then** devuelve **todas** las filas de A y **ninguna** de B.

### C4 — Contexto de company: un `user` solo ve su empresa dentro del tenant
- **Given** el tenant A con companies X e Y.
- **When** el rol runtime fija `app.tenant_id = A` y `app.company_id = X` y consulta `companies`.
- **Then** ve la company X y **no** la Y (misma asesoría, otra empresa → 0 filas de Y).

### C5 — Escribir en otro tenant se rechaza (WITH CHECK)
- **Given** el contexto `app.tenant_id = A`.
- **When** el rol runtime intenta **INSERT/UPDATE** de una fila con `tenant_id = B`.
- **Then** la operación se **rechaza** (violación de política RLS), no se escribe la fila.

### C6 — El rol runtime no puede desactivar ni saltarse la RLS
- **Given** el rol runtime conectado.
- **When** intenta `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` o `SET ROLE` al owner.
- **Then** falla por **falta de privilegios** (no es dueño ni superusuario; no tiene BYPASSRLS).

### C7 — El audit log es append-only a nivel de motor
- **Given** la tabla `audit_log`.
- **When** el rol runtime hace `INSERT` (permitido) y luego intenta `UPDATE` o `DELETE` de una entrada.
- **Then** el INSERT funciona y el UPDATE/DELETE **fallan por privilegios revocados** en Postgres.

### C8 — Toda tabla de negocio nace con RLS habilitada y forzada (guard anti-olvido)
- **Given** el esquema tras aplicar todas las migraciones.
- **When** se inspecciona `pg_class` para las tablas de negocio
  (`tenants`, `tenant_branding`, `users`, `companies`, `memberships`, `audit_log`).
- **Then** todas tienen `relrowsecurity = true` **y** `relforcerowsecurity = true`. Si una tabla de
  negocio no las tiene, el test falla (evita que una tabla futura olvide su RLS).

### C9 — El esquema `companies` encaja con los datos reales a importar (S1.5)
- **Given** las 60 empresas de `entregas/Empresas_CIF_NIF.xlsx` (columnas `Nombre`, `CIF/NIF`).
- **When** se crea una company con `name` y `cif` y `status = 'pending'`.
- **Then** la fila persiste con `tenant_id`, `name`, `cif`, `status ∈ {active, pending}`; `cif` admite
  tanto CIF de sociedad (`A39031620`) como NIF de autónomo (`76072394D`). (La validación del dígito de
  control y la importación son de S1.5; aquí solo se comprueba que el esquema los admite.)

## 4. Invariantes y reglas de negocio

- **Anti-cruce de tenants**: ninguna consulta del rol runtime cruza la frontera del tenant; el nivel
  company se respeta cuando hay `app.company_id`.
- **RLS FORCE en todas las tablas de negocio**; políticas por `app.tenant_id` (siempre) y `app.company_id`
  (cuando está fijada): `USING (tenant_id = app.tenant_id AND (app.company_id IS NULL OR company_id = app.company_id))`
  y el `WITH CHECK` equivalente en escritura.
- **El rol runtime es NOSUPERUSER, NOBYPASSRLS y no-owner.** Las migraciones las corre el rol owner.
- Toda tabla de negocio empieza su PK/índice por `tenant_id`.
- **`audit_log` append-only**: se revoca UPDATE y DELETE al rol runtime a nivel de Postgres.
- Variables de sesión con `SET LOCAL` (viven solo en la transacción); nunca fugan entre peticiones.

## 5. Casos límite y errores

- `app.tenant_id` con un UUID inexistente → 0 filas (como C2), sin error.
- `app.tenant_id` con valor no-UUID/basura → la política no casa → 0 filas o error controlado; nunca
  devuelve filas de otro tenant.
- Transacción que no fija las variables (bug de la capa app) → 0 filas (C1), nunca "todas".
- `platform_admin` y su acceso cross-tenant vía `panel.autoken.es` → **fuera de alcance** aquí.
- `cif_lookups` (caché global sin tenant) → fuera de alcance (se crea en Sprint 2, §11.8).

## 6. Fuera de alcance (no-objetivos)

- Login, JWT, 2FA, hashing de contraseñas (S1.3).
- Middleware subdominio→tenant y resolución HTTP (S1.2): aquí las variables de sesión se fijan a mano
  en los tests; el cableado HTTP es de S1.2.
- CRUD de companies e importador del Excel (S1.5).
- RBAC por endpoint (S1.6) y la suite anti-cruce como gate de CI (S1.7).
- Theming en runtime a partir de `tenant_branding` (frontend, sprints posteriores): aquí solo la tabla.
- Acceso cross-tenant de `platform_admin` (sprint de plataforma).
- Tablas de Sprint 2 (`invoices`, `ocr_*`, `counterparties`, `cif_lookups`).

## 7. Notas de verificación (cómo se prueba de extremo a extremo)

- Tests con **PostgreSQL real** (no SQLite: la RLS es específica de Postgres). Se necesita el servicio
  `postgres` disponible también en CI (job backend) → previsible ajuste del workflow para levantarlo.
- El test crea (con el rol owner) dos tenants y sus companies; luego, conectando como **rol runtime**,
  fija `SET LOCAL app.tenant_id`/`app.company_id` y verifica visibilidad (C1-C5), privilegios (C6-C7) y
  el guard de esquema (C8) leyendo `pg_class`.
- Semilla de datos: se puede usar un par de nombres/CIF reales del Excel para C9 (p. ej. `3L
  INTERNACIONAL / A39031620` y `ALBERTO CAÑA REGALADO / 76072394D`).
