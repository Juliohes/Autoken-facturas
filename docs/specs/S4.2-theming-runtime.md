# Spec: S4.2 Theming runtime

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Pendiente de aprobación de Julio antes de escribir tests.

- **ID / tarea:** S4.2 (Sprint 4 — Panel de plataforma + White-label + PWA multi-tenant).
- **Contexto (módulo):** `tenancy` (nuevo `tenancy/repository.py`, lectura de `tenant_branding`;
  amplía `GET /tenants/current`, S1.2) + frontend (nuevo hook + aplicación de tema).
- **ADR relacionados:** ninguno nuevo. No es el mismo problema que resolvió ADR-0013 (S4.1): esa
  enmienda trataba de un **endpoint autenticado** de `platform_admin`; `GET /tenants/current` ya era
  público desde S1.2, sin cambios en su modelo de autorización.
- **Estado:** propuesta, pendiente de aprobación
- **Investigado antes de escribir la spec:**
  - `GET /tenants/current` (público, S1.2) hoy devuelve solo `{slug, name, is_demo}`
    (`tenancy/router.py:22`); nada lee `tenant_branding` desde la API todavía (S4.1 solo escribe).
  - **No hace falta migración ni función `SECURITY DEFINER` nueva**: a diferencia de `tenants`
    (aislada por su propio `id`, el caso especial que sí necesitó `SECURITY DEFINER` en S1.2/S4.1),
    `tenant_branding` tiene RLS normal por `tenant_id` y el rol runtime **ya tiene** `SELECT` sobre
    ella (grant genérico de tablas de tenant, migración 0001). Con el `id` del tenant ya resuelto por
    el middleware (`request.state.tenant`), una `tenant_session(tenant.id)` corriente basta.
  - El frontend hoy no consume `GET /tenants/current` en ningún sitio (ni hook, ni componente). Sin
    variables CSS en uso en todo el proyecto (`grep "var(--"` → 0 resultados); Tailwind v3, config JS,
    con un comentario ya dejado en `tailwind.config.js` anticipando esta tarea.
  - `tenant_branding` no tiene ningún campo sensible (solo presentación: logo/colores/nombre/favicon);
    exponerlo en un endpoint ya público no cambia la superficie de riesgo.
- **Decisiones de dominio propuestas (a confirmar con la aprobación):**
  1. **`GET /tenants/current` se amplía** con `logo_url, color_primary, color_secondary, app_name,
     favicon` (los 5 campos de `tenant_branding`), todos `null` si el tenant no tiene branding (fila
     ausente o campos vacíos). El backend **nunca inventa un valor por defecto**: informa `null` tal
     cual; decidir qué se ve cuando falta es cosa del frontend (regla "nunca alucinar", igual criterio
     que el resto del proyecto).
  2. **Los valores por defecto ("Setex tal cual hoy") viven en el frontend**, no en el backend:
     `DEFAULT_APP_NAME = "Autoken Facturas"`, `DEFAULT_COLOR_PRIMARY = "#059669"` (el verde ya usado
     hoy en los botones principales, `bg-emerald-600`), `DEFAULT_COLOR_SECONDARY = "#0f172a"` (el
     fondo ya usado hoy, `bg-slate-900`, el mismo que ya fija `theme_color`/`background_color` del
     manifest PWA). Un tenant con `color_primary`/`color_secondary`/`app_name` a `null` debe verse
     visualmente **idéntico** a hoy.
  3. **Mecanismo: variables CSS en `:root`**, no una librería de temas. `useTenantTheme()` aplica
     `--color-primary`/`--color-secondary` con `document.documentElement.style.setProperty(...)` y
     cambia `document.title` a `app_name` (o al valor por defecto). Encaja con Tailwind v3 vía
     sintaxis de valor arbitrario (`bg-[var(--color-primary)]`) sin añadir ninguna dependencia nueva.
  4. **Alcance de esta tarea: el mecanismo + una prueba visible mínima, no un reskin completo.** Se
     aplica el tema (variables + título + logo, si lo hay) desde el punto de entrada actual de la app
     (`App.tsx`, hoy la única pantalla montada). **NO** se retocan los colores ya fijos de las
     pantallas existentes (`InvoicesPanel`, `CompaniesPanel`, `ConfirmationScreen`...) para que
     empiecen a leer las variables: eso es un cambio transversal mayor, mejor hecho junto con la tarea
     de app-shell ya pendiente (routing/login/nav, detectada en S3.4), no aquí. El CA de la tarea pide
     "el frontend carga branding... como variables CSS", que es el mecanismo de carga, no una
     migración de cada pantalla.
  5. **`favicon` se guarda en la respuesta pero no se usa todavía**: el manifest/icono dinámico es
     S4.3, ya explícitamente aparte en el plan. Se incluye en el DTO para no tener que volver a tocar
     este endpoint cuando llegue esa tarea (mismo coste, un único `SELECT`).
  6. **Fallo silencioso y no bloqueante**: si `GET /tenants/current` falla (404 en el host de
     plataforma, red caída...) la app sigue arrancando con los valores por defecto, sin aviso visible
     al usuario — es una personalización cosmética, no una dependencia dura del arranque.

## 1. Problema y valor de dominio

Cada asesoría ya puede darse de alta con su logo y sus colores (S4.1), pero hoy esos datos se quedan
sin usar: cualquier asesoría que entra ve el mismo Autoken Facturas genérico. Esta tarea hace que el
frontend, nada más cargar, pregunte "¿de qué asesoría es este subdominio y cómo se ve?" y aplique esa
identidad visual — sin que la asesoría original (Setex) note ningún cambio, porque no tiene branding
configurado y todo cae a los valores de hoy.

## 2. Lenguaje ubicuo

- **Branding del tenant**: `logo_url`, `color_primary`, `color_secondary`, `app_name`, `favicon` de
  `tenant_branding` (S4.1), expuestos vía `GET /tenants/current`.
- **Tema aplicado**: el efecto observable en el DOM — `document.title`, las variables CSS
  `--color-primary`/`--color-secondary` en `:root`, y el logo mostrado (si lo hay).

## 3. Comportamientos (criterios de aceptación)

> Backend observable vía HTTP (cliente ASGI, sin autenticar — el endpoint ya es público) contra
> Postgres real. Frontend observable montando `App` con la API mockeada (sin navegador real).

### Backend

#### C1 — El endpoint devuelve el branding completo cuando existe
- **Given** un tenant con `logo_url`, `color_primary`, `color_secondary` y `app_name` puestos
  (creado vía `POST /platform/tenants`, S4.1).
- **When** `GET /tenants/current` en su subdominio.
- **Then** responde 200 con esos 4 campos tal cual, más `slug`/`name`/`is_demo` (ya existentes).

#### C2 — El endpoint devuelve `null` cuando el tenant no tiene branding
- **Given** un tenant creado sin `logo_url`/colores (alta mínima, S4.1 C2).
- **When** `GET /tenants/current`.
- **Then** responde 200 con `logo_url`, `color_primary`, `color_secondary`, `favicon` a `null`;
  `app_name` es el que puso `create_tenant` por defecto (el `name` del tenant, spec S4.1 decisión 3).

#### C3 — Sigue siendo un 404 neutro cuando el host no resuelve
- **Given** un host que no es un tenant activo (plataforma, inexistente, suspendido).
- **When** `GET /tenants/current`.
- **Then** responde 404 (comportamiento ya existente, sin cambios).

#### C4 — Anti-cruce: el branding de un tenant no se filtra desde el subdominio de otro
- **Given** dos tenants con branding distinto.
- **When** se pide `GET /tenants/current` desde el subdominio de cada uno.
- **Then** cada respuesta trae solo su propio branding (RLS de `tenant_branding`, sin excepción).

### Frontend

#### C5 — Con branding, aplica colores y título del tenant
- **Given** `GET /tenants/current` responde con `app_name="I-Lex"`, `color_primary="#112233"`,
  `color_secondary="#445566"`.
- **When** se monta la app.
- **Then** `document.title` pasa a `"I-Lex"`; `--color-primary`/`--color-secondary` en `:root` valen
  `#112233`/`#445566`.

#### C6 — Sin branding, aplica los valores por defecto (Setex igual que hoy)
- **Given** `GET /tenants/current` responde con `app_name`, `color_primary`, `color_secondary` a
  `null`.
- **When** se monta la app.
- **Then** `document.title` es `"Autoken Facturas"`; las variables CSS valen `#059669`/`#0f172a`
  (decisión de dominio 2) — idéntico al comportamiento de hoy sin esta tarea.

#### C7 — Con logo, se muestra; sin logo, no hay hueco vacío
- **Given** `logo_url` presente.
- **When** se monta la app.
- **Then** se renderiza una imagen con ese `src`. Sin `logo_url`, no se renderiza ninguna imagen (no
  un icono roto ni un espacio reservado vacío).

#### C8 — Un fallo al cargar el tenant no bloquea ni rompe el arranque
- **Given** `GET /tenants/current` responde 404 o falla.
- **When** se monta la app.
- **Then** la app sigue mostrando su contenido (healthcheck de Fase 0) con los valores por defecto,
  sin ningún mensaje de error visible por esto.

## 4. Invariantes y reglas de negocio

- **El backend nunca inventa un valor de branding**: campo ausente en `tenant_branding` -> `null` en
  la respuesta, nunca un texto/color por defecto puesto por el servidor (decisión de dominio 1).
- **Anti-cruce**: la lectura de branding pasa por la RLS estándar de `tenant_branding` (`tenant_id`),
  sin ninguna vía que la salte.
- **El tema es cosmético, no bloqueante**: ningún fallo de esta tarea puede impedir que la app cargue
  (decisión de dominio 6).

## 5. Casos límite y errores

- **Un campo de branding presente y otros no** (p. ej. solo `color_primary`): cada campo se aplica o
  cae a su propio valor por defecto de forma independiente (no es todo-o-nada).
- **Host de plataforma (`panel`)**: `GET /tenants/current` da 404 ahí (no es un tenant); la app de
  plataforma (S4.1) siempre ve los valores por defecto. Correcto y esperado, no es un caso a arreglar.

## 6. Fuera de alcance (no-objetivos)

- **Retocar las pantallas ya existentes** para que usen las variables CSS en vez de sus clases
  Tailwind fijas: decisión de dominio 4, tarea aparte (junto con el app-shell).
- **Favicon/manifest dinámico**: S4.3.
- **Editar el branding de un tenant ya creado**: no hay endpoint de edición hoy (S4.1 solo dio alta);
  fuera de esta tarea.
- **Modo demo, custom domains, métricas, ciclo de vida**: S4.4-S4.7.

## 7. Notas de verificación (cómo se prueba de extremo a extremo)

- **Backend**: se crea un tenant con y sin branding (helpers ya existentes de S4.1) y se llama a
  `GET /tenants/current` sin autenticar, vía cliente ASGI, comparando la respuesta JSON. C4 siembra
  dos tenants y pide cada endpoint por su propio subdominio.
- **Frontend**: se mockea `api.GET('/api/v1/tenants/current')` con distintos escenarios (con
  branding, sin branding, error) y se monta `App`; se comprueba `document.title` y
  `document.documentElement.style.getPropertyValue(...)` tras el efecto, y la presencia/ausencia de
  la imagen del logo por `alt`/`role`.
