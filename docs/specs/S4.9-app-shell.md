# Spec: S4.9 App-shell (login real + routing + menú)

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Aprobada por autoindicación de Julio (2026-07-24): "dejar todo cerrado antes de seguir con el sprint 5" —
> primera tarea del nuevo lote de cierre de backlog (orden acordado: app-shell → S2.2 → interruptor
> admin-tech + S2.9/S2.10 + S4.8).

- **ID / tarea:** S4.9 (nueva; cierra el hallazgo transversal de S3.4 "falta una tarea de integración que
  conecte las pantallas entre sí antes de un demo end-to-end", CLAUDE.md "Estado actual").
- **Contexto (módulo):** 100% frontend. Nuevo: `frontend/src/features/session/` (contexto de sesión),
  `frontend/src/app/` (shell, router, menú). Toca `App.tsx`, `main.tsx`, `api/client.ts`. No añade ni
  modifica ningún endpoint de backend (el contrato ya existe completo: `POST /auth/login`,
  `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me`).
- **ADR relacionados:** ADR-0012 (transporte de sesión: access token en memoria + `Authorization: Bearer`;
  refresh en cookie httpOnly). Ninguno nuevo.
- **Estado:** autoaprobada (autorización explícita de Julio, 2026-07-24)

- **Investigado antes de escribir la spec** (ver informe de exploración, resumen):
  - **No hay nada de infraestructura de app-shell hoy**: cero routing (`react-router-dom` no está
    instalado), cero estado de sesión (ni un solo `createContext` en todo `frontend/src`), cero
    almacenamiento de token, cero componente de menú. `App.tsx`/`main.tsx` son literalmente el
    placeholder de healthcheck de Fase 0.
  - **Las 5 pantallas de negocio ya están terminadas y probadas de forma aislada**, con una interfaz de
    entrada mínima y consistente, diseñada a propósito para que un futuro app-shell las monte sin
    tocarlas: `InvoiceHistory` (cero props), `InvoicesPanel` (cero props), `CompaniesPanel`
    (`onViewInvoices?` ya deja el hueco de navegación explícito, comentario propio: *"sin app-shell aún:
    el llamante decide cómo mostrarlo"*), `PlatformTenants` (cero props), `ConfirmationScreen`
    (`{ fileId, onConfirmed, onRetry }`).
  - **El backend ya tiene todo el contrato de auth necesario**: `POST /auth/login` (`{email, password,
    totp_code?}` → `{access_token, token_type}` + cookie httpOnly `refresh_token`), `POST /auth/refresh`,
    `POST /auth/logout`, `GET /auth/me` (`{id, email, role, tenant, company}`). 3 roles en
    `tenancy/constants.py`: `platform_admin`, `tenant_admin`, `user`. El RBAC por rol ya se aplica en el
    backend en cada endpoint (`require_roles`/`require_platform_admin`) — el frontend NUNCA es la única
    barrera, solo evita mostrar acciones que el backend rechazaría de todos modos.
  - **`useCurrentUser` (S3.5) ya sabe consumir `GET /auth/me`** pero nadie lo monta globalmente hoy (solo
    lo usa `ConfirmationScreen` de forma aislada para la casilla de factura de prueba). Se reutiliza tal
    cual dentro del contexto de sesión nuevo, sin reescribirlo.
  - **`useTenantTheme` (S4.2) es el único hook que corre hoy en la raíz de `App.tsx`** y es
    intencionalmente tolerante a fallos (no bloquea el arranque si el tenant no resuelve). Debe seguir
    montado una sola vez arriba del todo del shell nuevo, para que el branding se vea también en la
    pantalla de login.
  - **No hay ninguna UI de "subir factura nueva" hoy** (S2.1 solo construyó el endpoint de backend;
    S2.2 -captura guiada PWA- es la tarea que añadirá esa entrada real y está deliberadamente después de
    esta en el orden acordado). `InvoicesPanel` ya tiene un botón "ver" por fila que descarga el fichero
    (`downloadUrl.mutate`), pero ningún flujo lleva hoy a `ConfirmationScreen` con un `fileId` real.
  - **`openapi-fetch` soporta middlewares** (`api.use({ onRequest, onResponse })`), es el mecanismo nativo
    para inyectar `Authorization: Bearer` y para interceptar un 401 y reintentar tras refrescar, sin
    tener que tocar cada llamada individual de cada feature.
- **Decisiones de dominio propuestas (autoaprobadas):**
  1. **Librería de routing: `react-router-dom` (v6)**. Es la opción estándar del ecosistema React/Vite,
     sin alternativa mejor justificada para este proyecto; se añade como nueva dependencia de producción.
  2. **Sesión = contexto de React (`SessionProvider`) que guarda el `access_token` en memoria** (nunca en
     `localStorage`/`sessionStorage`, coherente con ADR-0012) **+ el resultado de `GET /auth/me`** (rol,
     tenant, empresa). Se expone vía un hook `useSession()`. El `access_token` en memoria se pierde al
     recargar la página a propósito (mismo criterio ya fijado por ADR-0012 al decidir "en memoria" en vez
     de almacenamiento persistente) — al recargar, el shell intenta un refresh silencioso contra
     `POST /auth/refresh` (la cookie httpOnly sigue viva) antes de mostrar login; si el refresh falla,
     login.
  3. **`api/client.ts` gana un middleware `onRequest`** que añade `Authorization: Bearer <token>` leyendo
     el token actual de un pequeño store fuera de React (un módulo con `getToken`/`setToken`, actualizado
     por `SessionProvider` vía `useEffect`) — necesario porque el cliente `api` es un singleton importado
     fuera del árbol de componentes, no puede leer el contexto de React directamente.
  4. **Un middleware `onResponse` intercepta cualquier 401** (salvo en las propias llamadas de
     `/auth/login`, `/auth/refresh`, `/auth/logout`, que se excluyen explícitamente para no entrar en
     bucle): intenta `POST /auth/refresh` una única vez; si obtiene un `access_token` nuevo, reintenta la
     petición original con él; si el refresh también falla, limpia la sesión y fuerza una redirección a
     `/login` (vía un evento/callback que `SessionProvider` expone, no importando el router dentro del
     middleware para no acoplar capas).
  5. **Rutas y menú por rol** (fijas para esta versión, sin configuración dinámica):
     - `platform_admin` → `/plataforma` (`PlatformTenants`). Sin acceso a ninguna otra ruta de negocio
       (esas pantallas asumen contexto de tenant que un `platform_admin` no tiene).
     - `tenant_admin` → `/facturas` (`InvoicesPanel`, ruta de inicio tras login), `/empresas`
       (`CompaniesPanel`), `/historial` (`InvoiceHistory`), `/confirmar/:fileId` (`ConfirmationScreen`,
       alcanzable hoy solo navegando manualmente a la URL con un `fileId` real ya existente en BD; la
       entrada real desde "subir factura" llega con S2.2).
     - `user` → `/historial`, `/confirmar/:fileId`. Sin `/facturas` ni `/empresas` (paneles de gestión,
       fuera del alcance de un usuario raso; el backend ya lo reforzaría con 403 si se fuerza la URL, pero
       el menú tampoco los ofrece).
     El menú (barra superior) muestra únicamente los enlaces de la lista de arriba según
     `useSession().user.role`, más un botón "Cerrar sesión" siempre visible.
  6. **`CompaniesPanel.onViewInvoices`** se conecta navegando a `/facturas?empresa=<id>` (query param que
     `InvoicesPanel` ya sabe leer como filtro, reutilizando su filtro de empresa existente — sin tocar
     `InvoicesPanel` si el filtro por query param no existiera ya como prop/estado interno compatible; si
     no fuera trivial reutilizar el filtro interno tal cual, se acepta que por ahora simplemente navegue a
     `/facturas` sin preseleccionar el filtro, documentado como límite conocido, no bloqueante).
  7. **Ruta raíz `/` redirige** a la ruta de inicio del rol (`/plataforma` o `/facturas` según corresponda)
     si hay sesión válida, o a `/login` si no la hay. Cualquier ruta protegida sin sesión válida redirige a
     `/login` conservando la URL destino para volver tras el login (query param `?next=`).
  8. **Cierre de sesión**: botón "Cerrar sesión" llama a `POST /auth/logout` (revoca el refresh en
     servidor) y, tenga éxito o no esa llamada, limpia el estado local y redirige a `/login` — no dejar
     nunca al usuario "atascado" logueado en el cliente si la llamada de red falla.
  9. **`useTenantTheme()` se monta una única vez en la raíz del shell** (antes de decidir login vs. rutas
     protegidas), igual que hoy en `App.tsx`, para que el branding se aplique también en la pantalla de
     login.

## 1. Problema y valor de dominio

Hoy existen 5 pantallas de negocio completas y probadas (historial, confirmación, panel de facturas,
empresas, plataforma), pero **no hay ninguna forma de que un usuario real llegue a ellas**: no hay login,
no hay navegación entre ellas, y `App.tsx` sigue siendo la pantalla de comprobación de salud de la Fase 0.
Sin esto no es posible hacer una demo de extremo a extremo de nada de lo construido hasta ahora, ni
darle acceso real a Julio o a un cliente.

## 2. Lenguaje ubicuo

- **Sesión**: el estado de "quién ha iniciado sesión ahora mismo" en el navegador — el `access_token` en
  memoria más el rol/tenant/empresa obtenidos de `/auth/me`.
- **Ruta protegida**: cualquier URL que exige sesión válida; sin sesión, redirige a `/login`.
- **Menú**: la barra de navegación superior, cuyos enlaces varían según el rol de la sesión activa.
- **Refresh silencioso**: intento automático de renovar la sesión contra `/auth/refresh` sin que el
  usuario tenga que volver a escribir su contraseña (al recargar la página, o tras un 401).

## 3. Comportamientos (criterios de aceptación)

> Frontend: React Testing Library + MSW/mocks del cliente API (mismo patrón ya usado en los tests
> existentes de cada feature), montando el árbol completo del shell (`SessionProvider` + router).

### Login

#### C1 — Login correcto lleva a la pantalla de inicio del rol
- **Given** un usuario `tenant_admin` sin sesión, en `/login`.
- **When** rellena email + contraseña correctos y envía.
- **Then** `POST /auth/login` se llama con esos datos; al recibir `access_token`, se consulta
  `GET /auth/me`; con el rol resuelto, se navega a `/facturas` (ruta de inicio de `tenant_admin`); el menú
  muestra los enlaces de `tenant_admin`.

#### C2 — Login con credenciales incorrectas muestra error, sin navegar
- **Given** la pantalla de login.
- **When** `POST /auth/login` responde 401.
- **Then** se muestra un mensaje de error legible; la URL sigue en `/login`; no se guarda ningún token.

#### C3 — Login con `totp_code` requerido
- **Given** un usuario con 2FA activado.
- **When** `POST /auth/login` responde indicando que falta el segundo factor (mismo contrato ya devuelto
  por el backend).
- **Then** el formulario muestra el campo de código TOTP y permite reenviar con él, sin perder el
  email/contraseña ya escritos.

### Sesión y rutas protegidas

#### C4 — Sin sesión, cualquier ruta protegida redirige a login
- **Given** ningún `access_token` en memoria (recién cargada la app, sin cookie de refresh válida).
- **When** se navega a `/facturas`, `/historial`, `/empresas`, `/plataforma` o `/confirmar/<id>`.
- **Then** redirige a `/login?next=<ruta original>`.

#### C5 — Refresh silencioso al recargar con cookie válida
- **Given** un usuario ya logueado (cookie `refresh_token` httpOnly viva) que recarga la página (se pierde
  el `access_token` en memoria a propósito, decisión de dominio 2).
- **When** el shell arranca.
- **Then** intenta `POST /auth/refresh` antes de mostrar login; si responde con un `access_token` nuevo,
  la sesión se restaura sin pedir credenciales y navega a la ruta pedida (o a la de inicio del rol si no
  había ninguna en curso).

#### C6 — Refresh fallido lleva a login
- **Given** ningún `access_token` en memoria y `POST /auth/refresh` responde 401 (cookie caducada o
  inexistente).
- **When** el shell arranca.
- **Then** se muestra `/login`, sin bucles ni reintentos adicionales.

#### C7 — Un 401 a media sesión dispara un refresh y reintenta la petición original
- **Given** una sesión activa cuyo `access_token` ha caducado en el servidor sin que el cliente lo sepa
  aún.
- **When** cualquier llamada de la app (p. ej. `InvoicesPanel` pidiendo su listado) responde 401.
- **Then** el middleware intenta `POST /auth/refresh` una vez; si tiene éxito, la petición original se
  reintenta automáticamente con el token nuevo y la pantalla nunca llega a mostrar un error al usuario;
  si el refresh también falla, se limpia la sesión y se redirige a `/login`.

#### C8 — El interceptor de 401 nunca entra en bucle con las propias rutas de auth
- **Given** el middleware de refresh activo.
- **When** el propio `POST /auth/login` o `POST /auth/refresh` responde 401.
- **Then** NO se dispara un nuevo intento de refresh sobre esa respuesta (excluidas explícitamente, ver
  decisión 4); el error se propaga tal cual a quien hizo la llamada.

### Menú y navegación por rol

#### C9 — El menú de `platform_admin` solo ofrece `/plataforma`
- **Given** una sesión con rol `platform_admin`.
- **Then** el menú muestra únicamente el enlace a plataforma (más "Cerrar sesión"); no aparecen
  `/facturas`, `/empresas` ni `/historial`.

#### C10 — El menú de `tenant_admin` ofrece facturas, empresas e historial
- **Given** una sesión con rol `tenant_admin`.
- **Then** el menú muestra `/facturas`, `/empresas`, `/historial` (más "Cerrar sesión"); no aparece
  `/plataforma`.

#### C11 — El menú de `user` solo ofrece historial
- **Given** una sesión con rol `user`.
- **Then** el menú muestra únicamente `/historial` (más "Cerrar sesión"); no aparecen `/facturas`,
  `/empresas` ni `/plataforma`.

#### C12 — "Ver facturas" desde una empresa navega al panel de facturas
- **Given** la pantalla de empresas (`CompaniesPanel`), con sesión `tenant_admin`.
- **When** se pulsa "Ver facturas" de una empresa concreta.
- **Then** navega a `/facturas` (con el filtro de esa empresa preseleccionado si es trivial reutilizar el
  filtro existente de `InvoicesPanel`, decisión de dominio 6; si no, navega sin preseleccionar, documentado
  como límite conocido).

#### C13 — Cerrar sesión limpia el estado y vuelve a login
- **Given** cualquier sesión activa.
- **When** se pulsa "Cerrar sesión".
- **Then** se llama a `POST /auth/logout`; independientemente de si esa llamada tiene éxito o falla, el
  `access_token` en memoria y el estado de `/auth/me` se limpian y la app navega a `/login`; una ruta
  protegida visitada justo después vuelve a redirigir a `/login` (C4).

### Branding

#### C14 — El branding del tenant se aplica también en login
- **Given** un tenant con logo/colores propios configurados (S4.2).
- **When** se visita `/login` sin sesión.
- **Then** el logo/colores/nombre del tenant se aplican igual que en el resto de la app (mismo
  `useTenantTheme`, montado una sola vez en la raíz, decisión 9).

## 4. Invariantes y reglas de negocio

- **El `access_token` nunca se persiste** en `localStorage`/`sessionStorage`/cookies no-httpOnly — solo
  vive en memoria de JavaScript (ADR-0012). El refresh token, gestionado enteramente por el navegador vía
  cookie httpOnly, nunca es legible ni manipulable desde JavaScript.
- **El frontend nunca es la única barrera de autorización**: ocultar una ruta/enlace por rol es solo
  cosmético/UX; el backend ya rechaza (401/403) cualquier intento de saltárselo por URL directa — esta
  spec no repite ni relaja ninguna comprobación de servidor.
- **Anti-cruce de tenants**: el shell no añade ningún filtrado propio de tenant/empresa; toda esa garantía
  sigue viviendo en el backend (RLS), como en el resto del proyecto.
- **Ninguna pantalla de negocio existente (`InvoiceHistory`, `ConfirmationScreen`, `InvoicesPanel`,
  `CompaniesPanel`, `PlatformTenants`) se modifica en su lógica interna** — el app-shell las monta y les
  pasa las props que ya aceptaban; si alguna necesita un cambio mínimo de props (p. ej. `CompaniesPanel`
  recibiendo ahora un `onViewInvoices` real en vez de nada), es cableado, no un cambio de comportamiento.

## 5. Casos límite y errores

- **Rol desconocido/inesperado en `/auth/me`** (dato corrupto o versión de API desalineada): tratar como
  "sin sesión válida" y redirigir a login, nunca mostrar un menú vacío o roto silenciosamente.
- **Refresh concurrente**: si dos peticiones distintas reciben 401 casi a la vez, evitar disparar dos
  `POST /auth/refresh` en paralelo (la segunda espera el resultado de la primera en curso) — evita
  invalidar el refresh token dos veces si el backend lo rota en cada uso.
- **Navegar directamente a `/confirmar/<id>` de un fichero de otro tenant/empresa**: el backend ya
  devuelve 404/403 según corresponda (RLS); el shell solo muestra ese error, no añade lógica nueva.

## 6. Fuera de alcance (no-objetivos)

- **Flujo de "subir factura nueva"**: no existe entrada real a `ConfirmationScreen` desde la UI todavía;
  la construye S2.2 (captura guiada PWA), siguiente tarea del lote.
- **Registro de nuevos usuarios / recuperación de contraseña / activación de cuenta**: el backend ya tiene
  `POST /auth/activate`/`activate/confirm`, pero conectarlos a pantallas propias no está pedido aquí; se
  documenta como hueco conocido, no bloqueante para el resto del app-shell.
- **Persistencia de la sesión entre pestañas/dispositivos** más allá del refresh por cookie ya existente.
- **Configuración dinámica de rutas/menú por tenant** (p. ej. ocultar `/empresas` para un tenant
  concreto): las rutas por rol de la decisión 5 son fijas para todos los tenants.
- **Rediseño visual del menú/layout** más allá de lo mínimo funcional (enlaces + botón de cerrar sesión);
  no es una tarea de UI/UX pulida, es de integración.

## 7. Notas de verificación

- **Frontend**: montar el árbol completo (`SessionProvider` + `BrowserRouter`/`MemoryRouter` + rutas) con
  el cliente API mockeado (mismo patrón `vi.mock('../../api/client', ...)` ya usado en los tests
