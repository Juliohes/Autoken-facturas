# Spec: S5.3 Backups + restore drill

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Aprobada por Julio antes de escribir tests.

- **ID / tarea:** S5.3
- **Contexto (módulo):** `jobs` (lógica de backup/restore), `shared` (cifrado del backup, config), `scripts` (CLI)
- **ADR relacionados:** ADR-0019 (nuevo, cifrado y alcance del backup de base de datos)
- **CA del plan maestro:** "backup nocturno cifrado a Hetzner funcionando; simulacro de restore completo
  documentado con tiempos."
- **Estado:** aprobada por Julio (decisión de alcance confirmada explícitamente antes de redactar, ver §0)

## 0. Decisión de alcance (confirmada por Julio antes de escribir esta spec)

Este entorno de trabajo no tiene credenciales de Hetzner (ni de ningún destino de almacenamiento
externo real). Julio confirmó explícitamente: construir el **mecanismo completo y verificable** —
backup cifrado de la base de datos real de este entorno + simulacro de restore completo con tiempos
medidos, contra Postgres real (Docker), sin mocks — y dejar **el cron nocturno real en la VPS + la
subida a un destino externo real (Hetzner u otro)** documentados como pendientes de una sesión futura
con esas credenciales. Mismo patrón ya usado en S4.6 (Caddy/TLS real) y S5.6 (despliegue real del
stack de monitorización).

## 1. Problema y valor de dominio

Si el servidor de producción se pierde (fallo de disco, error humano, ataque), toda la información de
todas las asesorías (facturas, usuarios, historial) desaparece con él salvo que exista una copia
recuperable en otro sitio. Un backup que "existe" pero nunca se ha probado a restaurar no es una
garantía real — la única forma honesta de confiar en un backup es haberlo restaurado de verdad y medido
cuánto tarda (para saber si el tiempo de recuperación es aceptable para el negocio).

## 2. Lenguaje ubicuo

- **Backup completo**: volcado (`pg_dump`, formato `custom`) de TODA la base de datos (todas las
  asesorías/tenants a la vez — el modelo es RLS de una sola base de datos compartida, ADR-0001, no una
  base de datos por tenant).
- **Cifrado del backup**: cifrado simétrico (AES-256-GCM) del propio fichero de volcado, con una clave
  dedicada (`BACKUP_ENCRYPTION_KEY`) **distinta** de `DB_ENCRYPTION_MASTER_KEY` (S5.2, cifrado de
  columnas). Son dos secretos con modelos de amenaza distintos: filtrar la clave de columnas no debe
  destapar los backups completos, y viceversa; rotar uno no debe forzar rotar el otro (ver ADR-0019).
- **Simulacro de restore ("restore drill")**: descifrar un backup y restaurarlo en una base de datos
  Postgres **nueva y vacía** (nunca la de origen), para demostrar de verdad que el backup sirve — no
  basta con que el fichero exista.
- **DSN admin**: cadena de conexión con privilegios de superusuario/bypass-RLS, la misma que ya usan
  las migraciones de Alembic y el script de rotación de clave (S5.2) — no un rol nuevo para esta tarea.

## 3. Comportamientos (criterios de aceptación)

### C1 — Un backup completo se genera cifrado, nunca en claro en disco
- **Given** una base de datos Postgres real con datos (varios tenants, empresas, facturas)
- **When** se ejecuta el script de backup contra esa base de datos
- **Then** se produce un único fichero en la ruta de destino que es el volcado cifrado; el volcado
  en claro nunca se escribe como fichero intermedio (se cifra en memoria, en el mismo proceso, antes
  de tocar disco).

### C2 — El backup no es legible ni restaurable sin la clave correcta
- **Given** un backup ya generado (C1)
- **When** se intenta interpretarlo directamente como un volcado de Postgres (sin descifrar) o se
  intenta el restore drill con una clave de descifrado distinta a la usada para cifrarlo
- **Then** falla de forma clara (nunca produce datos parciales o corrompidos silenciosamente).

### C3 — El restore drill reconstruye los datos exactamente en una base nueva
- **Given** un backup cifrado de una base de datos con contenido conocido (recuento de filas conocido
  en varias tablas, incluidas columnas cifradas por S5.2)
- **When** se ejecuta el restore drill contra una base de datos Postgres nueva y vacía, con la clave
  correcta
- **Then** todas las tablas existen en el destino con el mismo recuento de filas que el origen, y el
  contenido de columnas cifradas (S5.2) es byte a byte idéntico (demuestra que el volcado no corrompe
  ni reinterpreta el `bytea` cifrado).

### C4 — El restore drill nunca sobrescribe una base de datos con datos
- **Given** una base de datos destino que YA tiene al menos una tabla de usuario con datos
- **When** se intenta un restore drill contra ella
- **Then** se rechaza explícitamente antes de tocarla, con un mensaje claro (protección contra
  destruir por error un entorno real apuntando el drill al sitio equivocado).

### C5 — El backup falla de forma ruidosa, nunca en silencio
- **Given** que `pg_dump` termina con error (credenciales inválidas, base inexistente) o falta la
  clave de cifrado configurada
- **When** se ejecuta el script de backup
- **Then** el proceso termina con código de salida distinto de cero y un mensaje claro; NUNCA deja un
  fichero de backup parcial o corrupto en la ruta de destino final (escritura atómica: fichero
  temporal + renombrado solo tras éxito completo).

### C6 — El simulacro mide y reporta tiempos reales
- **Given** un restore drill completo (C3)
- **When** termina
- **Then** devuelve/imprime al menos: tamaño del backup, duración del propio backup (si se mide en la
  misma ejecución) y duración del restore — datos que se documentan en el runbook (§7) como medición
  empírica real, no una estimación.

### C7 — Un backup de una base de datos vacía también funciona
- **Given** una base de datos recién creada, con el esquema de migraciones aplicado pero sin ningún
  tenant/fila de negocio
- **When** se hace backup y luego restore drill
- **Then** funciona igual que con datos (ninguna tabla, ninguna fila — pero el esquema y las 0 filas
  coinciden exactamente entre origen y destino).

## 4. Invariantes y reglas de negocio

- Anti-cruce de tenants: el backup es de TODA la base compartida (por diseño, ADR-0001) — no aplica
  aislamiento por tenant a este nivel; el destino cifrado y su control de acceso son la única barrera.
- La clave de cifrado del backup (`BACKUP_ENCRYPTION_KEY`) nunca se pasa por argumento de línea de
  comandos (mismo hallazgo de auditoría que `DB_ENCRYPTION_MASTER_KEY_NEW` en S5.2: visible en `ps`) —
  siempre por variable de entorno o `Settings`.
- El script nunca ejecuta el volcado/restore a través de un shell interpretado (subprocess con lista de
  argumentos, nunca `shell=True`) — evita inyección de comandos si algún parámetro viniera de fuera.
- El restore drill es una operación de solo lectura respecto al backup de origen y respecto a la base
  de datos de origen real: solo escribe en la base de datos destino, que debe ser distinta y vacía.

## 5. Casos límite y errores

- Clave de descifrado incorrecta: error claro de descifrado (autenticación AEAD fallida), nunca datos
  "restaurados" corruptos en silencio.
- Fichero de backup truncado/corrupto: `pg_restore` o el propio descifrado fallan con error claro.
- Base de datos destino inexistente (no creada de antemano): error claro, no se crea implícitamente
  (crear una base de datos nueva es una decisión explícita del operador, fuera de este script).
- Backup de una base de datos vacía (C7): no es un caso de error, es un camino feliz más.

## 6. Fuera de alcance (no-objetivos)

- Cron nocturno real ejecutándose en la VPS de producción (ver §0) — se documenta en el runbook como
  pendiente de una sesión futura con acceso a esa infraestructura.
- Subida real a Hetzner (o cualquier destino remoto real) — el script escribe a una ruta de fichero
  local; conectar esa ruta a un destino remoto real (rclone/rsync/SFTP a Hetzner Storage Box) es un
  paso de infraestructura documentado como pendiente (§0), no código de esta tarea.
- Backups incrementales, WAL archiving o point-in-time recovery: solo backup completo (`pg_dump`) por
  ahora — decisión explícita de alcance mínimo.
- Política de retención/rotación de backups antiguos (cuántos días guardar): se documenta como
  recomendación en el runbook, no se implementa código para ello.
- Backup de los objetos de MinIO (ficheros de facturas): el CA del plan maestro es específicamente
  sobre la base de datos; los ficheros ya tienen su propio mecanismo de export por tenant (S4.7,
  `export_tenant`) — se documenta la diferencia, no se construye un backup de objetos nuevo aquí.
- Crear o decidir un rol de Postgres nuevo para backups en producción: se reutiliza el mismo DSN admin
  que ya usan las migraciones/la rotación de clave (S5.2) — no es una decisión nueva de esta tarea.

## 7. Notas de verificación (cómo se prueba de extremo a extremo)

- Contra Postgres real de este entorno de trabajo (mismo contenedor de test usado por el resto de la
  suite), con datos sembrados de verdad (varios tenants, empresas, facturas, alguna columna cifrada de
  S5.2) — nunca mocks de `pg_dump`/`pg_restore`.
- Backup → restore drill contra una base de datos Postgres nueva y vacía creada solo para el drill →
  comparación de recuentos de filas y de contenido de columnas cifradas entre origen y destino.
- Tiempos y tamaño reales de la ejecución del drill se documentan en
  `docs/runbooks/backups-restore.md` tras la primera ejecución empírica (mismo patrón que S5.5:
  números reales, no estimados).
