# Spec: S2.4 Pantalla de confirmación (revisión y guardado)

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Aprobada por Julio antes de escribir tests.

- **ID / tarea:** S2.4 (Sprint 2 — Intake + OCR)
- **Contexto (módulo):** `frontend/` (pantalla React/PWA) + una pequeña ampliación del `GET
  /uploads/{id}/review` del backend (`invoicing`, S2.5) para exponer los motivos de bloqueo.
- **ADR relacionados:** ADR-0011 (veredicto del CIF de contraparte), ADR-0016 (el worker marca, el humano
  confirma), ADR-0006 (recibidas editables). Ninguno nuevo.
- **Estado:** aprobada por Julio (2026-07-13) — con vitest y `blocking_reasons` en el review

## 1. Problema y valor de dominio

Es la pantalla donde el humano **revisa** lo que leyó la IA y **confirma** (o repite la foto). Reproduce la
de la v1 (empresa IA / receptor / fecha / total / tramos IVA editables / IRPF / resumen / Confirmar / Repetir
foto) con los refuerzos de §11.8: **tres campos siempre visibles** (importe total, CIF de contraparte, fecha)
y el resto plegado; **colores de confianza** (amarillo = dudoso, rojo = no leído); **bloque de veredicto del
CIF de contraparte**; **checkbox de responsabilidad**; y el botón **"Confirmar y guardar" deshabilitado**
cuando el guardado sería inválido, con un **aviso rojo** debajo. La pantalla es una **comodidad**: la frontera
de seguridad la reimpone el backend (S2.5); aquí se replica para que el usuario no envíe algo que se va a
rechazar.

## 2. Lenguaje ubicuo

- **Datos de revisión**: respuesta del `GET /uploads/{id}/review` (S2.5): `fields` (issue_date, total_amount,
  net_amount, tax_amount, counterparty_tax_id, counterparty_name, tax_lines), `confidences` (por campo:
  `alta`/`media`/`baja`/`null`), `counterparty_verdict` (`status`/`name_match`/`official_name`), `own`
  (`cif`/`name` propios), `warnings`, y **`blocking_reasons`** (ampliación de S2.4, ver §6-backend).
- **Confianza por campo** → color: `alta` normal; `media` = **dudoso** (amarillo); `baja` o ausente/`null` =
  **no leído** (rojo). Solo pinta los campos de oro (fecha, importes, CIF de contraparte); la identidad propia
  se conoce (no se puntúa).
- **Motivos de bloqueo** (`blocking_reasons`, lista): los que el servidor reimpondría en `confirm`
  (`counterparty_cif_invalid`, `counterparty_cif_not_found`, `own_tax_id_missing`). Lista vacía = confirmable.
  Se calcula en el backend (misma lógica que las guardas de `confirm`, incluida la excepción de admin), para
  que el botón y la guarda del servidor estén **en sincronía** (única fuente de verdad).
- **Aceptación de responsabilidad**: checkbox obligatorio (regla 8). Estado del cliente; sin marcar, el botón
  está deshabilitado aunque no haya motivos de bloqueo.
- **Botón "Confirmar y guardar"**: **habilitado solo si** `blocking_reasons` está vacío **y** el checkbox está
  marcado. Al pulsarlo hace `POST /uploads/{id}/confirm` con los valores (editados) + `responsibility_accepted`.
- **Repetir foto**: botón que descarta la revisión y vuelve a la captura (S2.2). Aquí invoca un callback
  `onRetry` (la navegación/captura es de S2.2); el botón existe y es operable.

## 3. Comportamientos (criterios de aceptación)

> Frontend: componente `ConfirmationScreen` probado con **vitest + @testing-library/react** (jsdom, sin
> navegador) con el cliente de API **mockeado** (se inyectan respuestas de `review`/`confirm`). El motor real
> y el backend no se llaman en estos tests. Backend: un test de que `review` devuelve `blocking_reasons`.

### Render y jerarquía

#### C1 - Tres campos siempre visibles; el resto plegado
- **Given** unos datos de revisión.
- **When** se pinta la pantalla.
- **Then** el **importe total**, el **CIF de contraparte** (con su veredicto) y la **fecha** están visibles sin
  desplegar; el resto (nº factura, nombres, tramos de IVA, IRPF, datos propios) está en un desplegable plegado
  por defecto.

#### C2 - Colores de confianza por campo
- **Given** `confidences` con un campo `media` y otro `baja`/ausente.
- **When** se pinta.
- **Then** el campo `media` se marca **dudoso** (amarillo) y el `baja`/ausente **no leído** (rojo); un campo
  `alta` no lleva marca de aviso.

#### C3 - Bloque de veredicto del CIF de contraparte
- **Given** `counterparty_verdict`.
- **When** se pinta.
- **Then** se muestra el estado: `valid`+`name_match` → verde; `valid`+`name_match=false` → **aviso con la
  razón social oficial** (`official_name`); `invalid`/`not_found` → rojo; `unverified` → aviso "revisar manual".

### Botón "Confirmar y guardar" (deshabilitado por condición)

#### C4 - CIF de contraparte inválido deshabilita el botón
- **Given** `blocking_reasons` incluye `counterparty_cif_invalid`.
- **When** se pinta (con el checkbox marcado).
- **Then** el botón "Confirmar y guardar" está **deshabilitado**.

#### C5 - CIF de contraparte inexistente deshabilita el botón
- **Given** `blocking_reasons` incluye `counterparty_cif_not_found`.
- **Then** el botón está **deshabilitado** (checkbox marcado).

#### C6 - CIF propio ausente deshabilita el botón
- **Given** `blocking_reasons` incluye `own_tax_id_missing`.
- **Then** el botón está **deshabilitado** (checkbox marcado).

#### C7 - Sin aceptar la responsabilidad, el botón está deshabilitado
- **Given** `blocking_reasons` vacío pero el checkbox **sin marcar**.
- **Then** el botón está **deshabilitado**. Al marcar el checkbox (sin motivos de bloqueo) → **habilitado**.

#### C8 - Sin bloqueos y con responsabilidad, confirma
- **Given** `blocking_reasons` vacío y el checkbox marcado.
- **When** el usuario pulsa "Confirmar y guardar".
- **Then** se hace `POST /uploads/{id}/confirm` con los valores mostrados + `responsibility_accepted: true`; al
  responder 201, se invoca `onConfirmed` (éxito).

### Avisos y acciones

#### C9 - Aviso rojo de responsabilidad siempre bajo el botón
- **Given** cualquier estado.
- **When** se pinta.
- **Then** bajo el botón hay un aviso en rojo, grande y legible: *"Revisa bien los datos antes de confirmar:
  su veracidad es responsabilidad de quien los confirma."*

#### C10 - Descuadre aritmético marcado
- **Given** `warnings` incluye el descuadre (o el total no cuadra con los tramos).
- **When** se pinta.
- **Then** se muestra un aviso de descuadre "Revisar" (no bloquea el botón; regla 5).

#### C11 - Repetir foto
- **Given** la pantalla.
- **When** el usuario pulsa "Repetir foto".
- **Then** se invoca `onRetry` (descarta la revisión; la captura es S2.2).

#### C12 - Rechazo del servidor se muestra sin perder los datos
- **Given** el botón habilitado (el cliente creía que era confirmable).
- **When** `POST confirm` responde 4xx (el servidor reimpone una guarda: p. ej. 422/409).
- **Then** se muestra el error de forma legible y **no** se pierde lo editado; no se navega a éxito.

### Backend (ampliación de `review`)

#### C13 - `review` devuelve `blocking_reasons`
- **Given** un `uploaded_file` cuyo CIF de contraparte es inválido (o el CIF propio no aparece y el actor no es
  admin).
- **When** se hace `GET /uploads/{id}/review`.
- **Then** la respuesta incluye `blocking_reasons` con el/los motivo(s) (`counterparty_cif_invalid` /
  `own_tax_id_missing`); con todo correcto y confirmable, `blocking_reasons` es una lista vacía. Se calcula con
  la **misma** lógica que las guardas de `confirm` (incluida la excepción de admin).

## 4. Invariantes y reglas de negocio

- **El botón no es la seguridad**: el backend (S2.5) reimpone las guardas en `confirm`; la pantalla las
  **replica** desde `blocking_reasons` (única fuente de verdad, calculada en servidor) para no dejar enviar algo
  que se rechazará. Si el servidor rechaza igualmente (C12), se muestra el error.
- **Responsabilidad obligatoria**: sin el checkbox marcado, no se puede confirmar (regla 8).
- **Anti-alucinación visible**: un campo no leído se pinta en rojo (no en blanco como si fuera correcto); nunca
  se muestra un valor inventado (el backend ya lo garantiza; la pantalla lo hace evidente).
- **Jerarquía**: total + CIF de contraparte + fecha siempre visibles; el resto plegado (regla 12).
- **Identidad propia conocida**: se muestra desde `own` (no editable como lectura); no se puntúa su confianza.
- **Descuadre = aviso**, no bloqueo (regla 5).

## 5. Casos límite y errores

- **`review` responde 403/404/409** (fichero ajeno / otro tenant / no confirmable): la pantalla muestra el
  estado correspondiente (sin datos), no un formulario vacío editable.
- **Campo ausente** en `fields` (p. ej. total `null`): se pinta como "no leído" (rojo), editable; no se
  inventa un valor.
- **`unverified`** (fuente externa caída): no bloquea; se marca "revisar manual" y el botón puede habilitarse
  (si el checkbox está marcado y no hay otros bloqueos).
- **Envío en curso**: el botón se deshabilita mientras el `POST confirm` está en vuelo (evita doble envío).

## 6. Fuera de alcance (no-objetivos)

- **Captura / cámara / recorte / auto-captura / selector Recibida-Emitida**: S2.2. Aquí "Repetir foto" es un
  callback; la `direction` se recibe/propaga pero su selección es de S2.2.
- **Historial, panel, export**: S2.6 / S3.x.
- **Edición auditada post-confirmación** e inmutabilidad de emitidas: S3.3.
- **Estilos pixel-perfect** de la v1: se replica la estructura y las reglas, no un clon exacto de CSS.
- **Prueba en dispositivos Android/iOS reales**: es criterio de **S2.2** (captura); S2.4 se valida con tests de
  componente (vitest/jsdom), que cubren la lógica de la pantalla sin navegador.

## 7. Notas de verificación (cómo se prueba de extremo a extremo)

- **Frontend**: se añade el framework de test **vitest** + **@testing-library/react** + **jsdom** a
  `frontend/` (no existía) y el script `test`. El componente `ConfirmationScreen` se prueba con el cliente de
  API **mockeado** (respuestas de `review`/`confirm` inyectadas): C1-C12. Sin navegador ni backend reales.
- El **cliente de API tipado** se regenera desde el OpenAPI del backend (`npm run gen:api` sobre un
  `openapi.json` actualizado con `review`/`confirm` y el nuevo `blocking_reasons`), para que la pantalla
  consuma tipos reales (no `any`).
- **Backend**: se amplía `invoicing.service.review` / `ReviewData` con `blocking_reasons: list[str]`, calculado
  por una función compartida con las guardas de `confirm` (misma lógica, incluida la excepción de admin). Test
  C13 en `backend/tests/test_invoice_confirm.py` (review de un CIF inválido / CIF propio ausente → motivos;
  confirmable → lista vacía). El OpenAPI regenerado refleja el campo nuevo.
- **CI**: el job de frontend (typecheck + lint + build) debe seguir verde; se añade la ejecución de `vitest`
  (los tests de componente) al pipeline de frontend.
