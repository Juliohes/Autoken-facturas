# Spec: S4.10 Interruptor admin-tech

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Aprobada por autoindicación de Julio (2026-07-24): tercera tarea del lote de cierre de backlog
> previo al Sprint 5 (S4.9 → S2.2 → **S4.10** → S2.9/S2.10 → S4.8). Modelo de "admin-tech" confirmado
> explícitamente por Julio tras preguntarle: **flag sobre una cuenta `platform_admin` ya existente**
> (no un rol nuevo en el enum cerrado).

- **ID / tarea:** S4.10 (nueva; prerrequisito común de S2.9/S2.10 y S4.8, decisión de Julio del
  2026-07-22, `decisiones-2026-07-22-preprocesado-multimodelo` en memoria del proyecto — "antes hace
  falta construir un interruptor solo para Julio").
- **Contexto (módulo):** `platform_admin` (submódulo nuevo, `settings_router.py`/`settings_service.py`/
  `settings_repository.py`, mismo patrón ya establecido por `tenants_router.py`) + `identity` (el
  flag `is_admin_tech` se añade a `AuthContext`/`MeOut`) + frontend `features/platform/`.
- **ADR relacionados:** ninguno nuevo; sigue el patrón `SECURITY DEFINER` ya usado en todo
  `platform_admin` desde S4.1.
- **Estado:** autoaprobada (autorización explícita de Julio, 2026-07-24; modelo de datos confirmado
  tras preguntarle)

- **Investigado antes de escribir la spec:**
  - **Hoy no hay ninguna forma de distinguir a Julio de un futuro segundo `platform_admin`** (p. ej.
    Alberto): el modelo `User` (`tenancy/models.py`) no tiene ningún campo de este tipo, y el
    `Role` enum (`tenancy/constants.py`) es un `StrEnum` cerrado con CHECK de Postgres
    (`platform_admin`/`tenant_admin`/`user`), sin cuarto valor.
  - **No existe ninguna tabla de configuración global** en las 15 migraciones actuales
    (`backend/migrations/versions/0001`-`0015`) — solo `tenants`/`tenant_branding`. Hace falta una
    tabla nueva desde cero.
  - **Patrón ya establecido en `platform_admin/`** (S4.1-S4.7): router fino (HTTP) + service (dominio)
    + repository (SQL puro, siempre contra funciones `SECURITY DEFINER`) + guard
    `require_platform_admin()`. El submódulo de ajustes reutiliza este mismo patrón, con un guard
    adicional (`require_admin_tech()`) que exige además el flag.
  - **`GET /auth/me` (`MeOut`)** ya es el único sitio donde el frontend conoce el rol de la sesión
    activa (S4.9); añadir `is_admin_tech: bool` ahí es aditivo (campo nuevo, no rompe nada existente)
    y evita inventar un segundo endpoint de "quién soy".
  - **Frontend**: `Role` (union type cerrado a 3 valores, `features/session/SessionProvider.tsx`) NO
    se toca — el flag es una dimensión de visibilidad *adicional* dentro de `platform_admin`, no un
    rol nuevo. `ROUTE_DEFS` (`app/routes.ts`) sigue siendo puramente por rol; la comprobación del
    flag vive dentro de la propia pantalla nueva, no en el enrutador genérico (evita complicar la
    tabla rol→ruta para un único caso de "rol + condición extra").
  - **Fuera de alcance de esta tarea**: el propio comportamiento de S2.9/S2.10 (preprocesado +
    comparativa) y S4.8 (panel multi-modelo) — esta tarea construye SOLO el mecanismo del
    interruptor (columna/flag + tabla de ajuste + endpoint + pantalla mínima), sin enganchar todavía
    ninguna llamada OCR real a él. Las tareas siguientes leerán este flag, no lo construyen.
  - **Nota para las tareas siguientes** (no se decide ni se construye aquí, solo se deja constancia):
    al investigar el pipeline OCR (`jobs/ocr.py::run_ocr`) para entender dónde engancharía S4.8, se
    confirmó que ya existe la abstracción de N extractores en paralelo (`asyncio.gather` +
    `ocr/arbiter.py::reconcile`) pensada para esto — pero los motores candidatos de
    `ocr/engines/registry.py` implementan la interfaz `OcrEngine` del bench, **no** la interfaz
    `InvoiceExtractor` que usa `run_ocr` en producción; solo `gemini_extractor.py` implementa
    `InvoiceExtractor` hoy. S4.8 tendrá que resolver esa discrepancia de interfaces — aviso para
    cuando llegue esa tarea, no bloquea S4.10.
- **Decisiones de dominio propuestas (autoaprobadas):**
  1. **`users.is_admin_tech boolean NOT NULL DEFAULT false`**, columna nueva (migración), solo tiene
     sentido junto a `role = 'platform_admin'` (no se valida esa combinación a nivel de base de
     datos — un `tenant_admin`/`user` con el flag a `true` simplemente no lo usaría nunca porque
     todos los guards exigen `platform_admin` primero — pero se documenta como invariante de negocio,
     no de esquema, para no acoplar dos columnas con un CHECK cruzado innecesario).
  2. **Sin ningún endpoint que active este flag desde la aplicación**: se activa a mano en Postgres,
     igual que hoy se da de alta el primer `platform_admin` (fuera de repo, documentado en
     S1.3). No se construye un "gestor de administradores" — sería una superficie nueva no pedida,
     para un caso de uso de un único usuario (Julio) en un experimento acotado en el tiempo.
  3. **Tabla nueva `platform_settings`**: una sola fila (o clave fija), con la columna
     `ocr_experiment_enabled boolean NOT NULL DEFAULT false` — el interruptor único que gobierna
     S2.9/S2.10 y S4.8 a la vez (Julio los describió como "este modo experimental" en singular, un
     interruptor, no tres). Sin diseño genérico de "feature flags" (clave/valor abierto): sería
     abstracción especulativa para un único ajuste real hoy; si en el futuro hace falta un segundo
     ajuste global, se añade como columna nueva o se generaliza entonces, no antes (YAGNI).
  4. **`GET/PUT /platform/settings`**, protegidos con un guard nuevo `require_admin_tech()` (además
     de `platform_admin`, exige `is_admin_tech = true`) — un `platform_admin` sin el flag recibe 403,
     igual que hoy un `tenant_admin` intentando `/platform/tenants`. `GET` devuelve el estado actual;
     `PUT` cambia `ocr_experiment_enabled` (body `{"ocr_experiment_enabled": bool}`).
  5. **`MeOut` (`GET /auth/me`) gana `is_admin_tech: bool`**, calculado de la fila real del usuario
     (no del token — igual que `role`/`tenant`/`company` hoy, siempre se lee de la sesión de BD, spec
     S1.6). Un `tenant_admin`/`user` siempre lo recibe en `false` (el flag solo tiene sentido en
     `platform_admin`, pero el campo existe siempre para no complicar el tipo con un opcional que
     dependa del rol).
  6. **Frontend**: nueva ruta `/plataforma/ajustes` (`PlatformSettings.tsx`, pantalla propia, mismo
     patrón que el resto: un fichero por pantalla). Protegida a nivel de ruta por rol
     `platform_admin` (como `/plataforma`); dentro del propio componente, si `user.is_admin_tech` es
     `false`, se muestra un mensaje de "sin acceso" en vez del interruptor — la comprobación de flag
     vive en la pantalla, no en el router genérico (decisión ya explicada arriba). El enlace al menú
     ("Ajustes") solo aparece si `is_admin_tech` es `true` (un `platform_admin` sin el flag no ve el
     enlace, coherente con que tampoco vería nada útil si entrara).
  7. **El interruptor es de solo lectura/escritura de su propio estado**: esta tarea NO dispara
     ningún efecto real (no toca el pipeline OCR, no hace backfill). Es la última pieza de las 3 que
     se dijo, deliberadamente, iba primero — el "coste ~7-8 llamadas OCR extra" de la advertencia de
     Julio no aplica todavía a nada, porque nada consume el flag hasta S2.9/S2.10/S4.8.

## 1. Problema y valor de dominio

Julio decidió medir en producción, con datos reales, si el preprocesado de imagen y varios motores
OCR en paralelo mejoran la lectura de facturas — un experimento con coste real en llamadas a IA que
solo él debe poder encender o apagar. Hoy no existe ningún mecanismo para eso: ni una forma de
distinguirle de un futuro segundo administrador de plataforma, ni un sitio donde guardar "está
encendido o apagado". Esta tarea construye esa base, sin la cual S2.9/S2.10/S4.8 no se pueden
empezar con seguridad (activarían gasto real sin ningún interruptor que lo pare).

## 2. Lenguaje ubicuo

- **admin-tech**: un `platform_admin` con el flag `is_admin_tech = true` — hoy, solo Julio.
- **Interruptor / experimento OCR**: el ajuste único `ocr_experiment_enabled` de `platform_settings`
  que S2.9/S2.10/S4.8 leerán (en tareas futuras) para decidir si disparan sus llamadas extra.

## 3. Comportamientos (criterios de aceptación)

> Backend observable vía HTTP (cliente ASGI autenticado) contra Postgres real.

### Acceso

#### C1 — Un `platform_admin` sin el flag no puede leer ni cambiar el ajuste
- **Given** un usuario `platform_admin` con `is_admin_tech = false`.
- **When** `GET /platform/settings` o `PUT /platform/settings`.
- **Then** 403 en ambos casos.

#### C2 — Un `platform_admin` con el flag sí puede
- **Given** un usuario `platform_admin` con `is_admin_tech = true`.
- **When** `GET /platform/settings`.
- **Then** 200 con `{"ocr_experiment_enabled": false}` (valor por defecto de una instalación nueva).

#### C3 — `tenant_admin`/`user` nunca pueden, aunque lo intenten directamente
- **Given** cualquier sesión `tenant_admin` o `user`.
- **When** `GET`/`PUT /platform/settings`.
- **Then** 403 (cubierto también por el guardián anti-olvido de `test_rbac.py`).

### Cambiar el ajuste

#### C4 — Encender el interruptor
- **Given** un admin-tech, ajuste en `false`.
- **When** `PUT /platform/settings` con `{"ocr_experiment_enabled": true}`.
- **Then** 200 con el nuevo estado; una lectura posterior (`GET`) confirma `true`.

#### C5 — Apagarlo de nuevo
- **When** `PUT` con `{"ocr_experiment_enabled": false}` sobre uno ya encendido.
- **Then** 200; `GET` posterior confirma `false`. Idempotente: apagar uno ya apagado también es 200.

### `GET /auth/me`

#### C6 — `is_admin_tech` refleja el flag real del usuario
- **Given** un `platform_admin` con `is_admin_tech = true`.
- **When** `GET /auth/me`.
- **Then** la respuesta incluye `is_admin_tech: true`.

#### C7 — Cualquier otro rol siempre ve `false`
- **Given** una sesión `tenant_admin` o `user` (o un `platform_admin` sin el flag).
- **When** `GET /auth/me`.
- **Then** `is_admin_tech: false`.

### Frontend

#### C8 — El enlace "Ajustes" solo aparece para admin-tech
- **Given** el menú de plataforma.
- **Then** aparece "Ajustes" únicamente si `user.is_admin_tech` es `true`; un `platform_admin` normal
  no lo ve.

#### C9 — Un `platform_admin` sin el flag que entra a `/plataforma/ajustes` a mano ve "sin acceso"
- **Given** la ruta `/plataforma/ajustes` visitada directamente (URL escrita a mano).
- **When** `user.is_admin_tech` es `false`.
- **Then** se muestra un mensaje de acceso denegado, nunca el interruptor.

#### C10 — Encender/apagar desde la pantalla
- **Given** un admin-tech en `/plataforma/ajustes`.
- **When** activa/desactiva el interruptor.
- **Then** llama a `PUT /platform/settings` con el nuevo valor; el interruptor de la UI refleja el
  estado confirmado por el backend (no un estado optimista sin confirmar, dado que activa gasto
  real).

## 4. Invariantes y reglas de negocio

- **El flag `is_admin_tech` nunca se puede activar desde la aplicación**: solo existe fuera de repo,
  a mano en Postgres, decisión de dominio 2.
- **`is_admin_tech` no sustituye ni relaja `require_platform_admin`**: siempre se exigen ambas
  condiciones (`role = platform_admin` Y `is_admin_tech = true`), nunca una sola.
- **Esta tarea no toca el pipeline OCR**: el ajuste se guarda y se lee, pero nada lo consume todavía.

## 5. Casos límite y errores

- **`platform_settings` sin fila** (instalación nueva, antes de cualquier migración de datos): la
  propia migración inserta la fila inicial con `ocr_experiment_enabled = false` — nunca hay un
  estado "sin ajuste todavía" observable desde la API.
- **`PUT` con un cuerpo inválido** (campo que falta, tipo incorrecto): 422, mismo criterio que el
  resto de endpoints del proyecto (validación Pydantic).

## 6. Fuera de alcance (no-objetivos)

- **El comportamiento real de S2.9/S2.10/S4.8**: esta tarea no preprocesa ninguna imagen ni llama a
  ningún motor OCR adicional.
- **Backfill retroactivo de facturas existentes**: mecanismo futuro de S2.9/S2.10/S4.8, no de esta
  tarea (el mecanismo de cola ya existe, `jobs/queue.py`, y se reutilizará entonces).
- **Gestión de administradores desde la aplicación** (dar/quitar `platform_admin` o el flag
  admin-tech a otros usuarios): decisión de dominio 2, fuera de alcance a propósito.
- **Historial de cambios del interruptor** (quién lo encendió/apagó y cuándo): no pedido; si hiciera
  falta auditoría de esto, ya existe `audit_log` como mecanismo general reutilizable en una tarea
  futura, no aquí.

## 7. Notas de verificación

- **Backend**: pruebas de comportamiento contra Postgres real, sembrando un `platform_admin` con y
  sin el flag (helper nuevo en `tests/_platform.py`, mismo patrón que `seed_tenant`/etc.).
- **Frontend**: pruebas de comportamiento mockeando `GET /auth/me` con `is_admin_tech` en ambos
  valores, verificando visibilidad del enlace y de la pantalla.
