# Spec: S5.6 Monitorización y alertas

> Spec-Driven Domain. Esta spec es la **fuente única** que alimenta los tests (TDD) y las 3 auditorías.
> Si algo no está aquí, no se implementa. Aprobada por Julio antes de escribir tests.

- **ID / tarea:** S5.6
- **Contexto (módulo):** shared (observabilidad transversal), jobs (salud de la cola OCR), infrastructure (Prometheus/Grafana/Alertmanager como código)
- **ADR relacionados:** ninguno nuevo
- **Estado:** aprobada por Julio (autoaprobación autorizada para el Sprint 5); decisiones de infraestructura confirmadas explícitamente por Julio (ver §0)

## 0. Decisiones de infraestructura (confirmadas por Julio, 2026-07-26)
- **Stack de Grafana**: self-hosted en la VPS B, como contenedores más en `infrastructure/docker-compose.yml`
  (Prometheus + Grafana + Alertmanager + node-exporter), no una cuenta SaaS.
- **Sentry**: se integra el SDK de forma que se activa SOLO si hay `SENTRY_DSN` configurado (mismo patrón
  que el resto de proveedores externos opcionales del proyecto); sin DSN, no hace nada — coste y riesgo
  cero. Julio no tiene cuenta todavía; se activa cuando la cree.

## 1. Problema y valor de dominio
Antes de producción, si el servicio cae, la cola de OCR se atasca, el disco se llena o la tasa de
errores 5xx se dispara, hoy nadie se entera hasta que un usuario se queja. Esta tarea da visibilidad
(qué está pasando ahora mismo) y aviso proactivo (alguien se entera antes de que un cliente lo note).

## 2. Lenguaje ubicuo
- **Cola OCR atascada**: hay trabajos pendientes en la cola de arq (`ocr_queue_name`) y el más
  antiguo lleva más tiempo esperando del que debería (el worker no los está consumiendo, o va más
  lento de lo que llegan).
- **Profundidad de cola**: número de trabajos pendientes (aún no empezados) en la cola.
- **Antigüedad del más viejo**: segundos transcurridos desde que se encoló el trabajo pendiente más
  antiguo. Ausente (`None`) si la cola está vacía — nunca `0` con el significado de "todo bien"
  cuando en realidad no hay datos.
- **Métrica**: valor numérico expuesto en formato Prometheus (`GET /metrics`), que Prometheus
  scrapea periódicamente y Grafana visualiza; las reglas de alerta de Alertmanager se evalúan sobre
  estas mismas métricas, no sobre una fuente distinta.

## 3. Comportamientos (criterios de aceptación)
> Alcance de esta sección: la instrumentación de aplicación (código), verificable con tests reales
> contra Postgres/Redis. La infraestructura (Prometheus/Grafana/Alertmanager como código) se describe
> en §7 con su propio criterio de verificación, al no ser comportamiento ejercitable por pytest.

### C1 — Sin DSN de Sentry configurado, no se inicializa nada
- **Given** `SENTRY_DSN` no está presente en el entorno
- **When** se construye la aplicación (`create_app()`)
- **Then** Sentry NO se inicializa (sin intento de red, sin coste, sin fallo de arranque).

### C2 — Con DSN de Sentry configurado, se inicializa con ese DSN
- **Given** `SENTRY_DSN` está presente en el entorno
- **When** se construye la aplicación
- **Then** el SDK de Sentry se inicializa exactamente una vez, con ese DSN y el entorno
  (`app_env`) de la aplicación.

### C3 — `GET /metrics` expone métricas en formato Prometheus
- **Given** la aplicación arrancada
- **When** se pide `GET /metrics`
- **Then** responde `200` con `Content-Type` de texto Prometheus, incluyendo un contador de
  peticiones HTTP (con su código de estado, para poder derivar la tasa de 5xx) y la métrica de
  profundidad de cola OCR (`autoken_ocr_queue_depth`).

### C4 — La profundidad de cola refleja los trabajos realmente pendientes
- **Given** N trabajos encolados en la cola de OCR de arq (Redis real) y ninguno consumido todavía
- **When** se pide `GET /metrics`
- **Then** `autoken_ocr_queue_depth` vale N.

### C5 — La antigüedad del más viejo refleja el tiempo real transcurrido
- **Given** un trabajo encolado hace más de un segundo y otro encolado justo ahora
- **When** se pide `GET /metrics`
- **Then** `autoken_ocr_queue_oldest_pending_seconds` es al menos el tiempo transcurrido desde el
  primero (nunca menor), no desde el segundo.

### C6 — Cola vacía no rompe nada
- **Given** ningún trabajo pendiente en la cola
- **When** se pide `GET /metrics`
- **Then** `autoken_ocr_queue_depth` vale `0` y no hay ninguna serie de "antigüedad" publicada (no
  se inventa un `0` que se leería como "todo al día" cuando en realidad no hay dato).

## 4. Invariantes y reglas de negocio
- `GET /metrics` NUNCA expone datos de negocio de un tenant concreto (ni facturas, ni CIFs, ni
  nombres): solo agregados operativos transversales (profundidad de cola, contadores HTTP). Mismo
  criterio que `platform_tenant_metrics` (S4.5): agregado, nunca detalle identificable.
- `GET /metrics` es público (sin autenticación de aplicación), como es estándar en el ecosistema
  Prometheus — se protege a nivel de red/firewall en producción (solo Prometheus interno puede
  alcanzarlo), no a nivel de aplicación. Decisión de dominio documentada aquí, no una omisión.
- Sentry nunca debe poder tumbar el arranque de la app si el DSN es inválido o la red falla al
  inicializar (fail-open para observabilidad: perder trazas de error es aceptable, perder el
  servicio entero por su culpa no).
- La métrica de cola usa la API pública de arq (`ArqRedis.queued_jobs()`), no claves de Redis
  reconstruidas a mano: si arq cambia su representación interna, esta métrica no se rompe en
  silencio con un número inventado.

## 5. Casos límite y errores
- Redis caído al pedir `/metrics`: la métrica de cola OCR se omite (o se marca como `NaN`/ausente),
  pero el resto de métricas (HTTP) se sirven igualmente — un fallo de Redis no debe tumbar todo el
  endpoint de métricas.
- Miles de trabajos pendientes: `queued_jobs()` los trae todos a memoria para calcular profundidad y
  antigüedad; aceptable para el volumen esperado de este proyecto (no hay miles de facturas
  simultáneas), documentado como límite conocido, no un problema de esta tarea.

## 6. Fuera de alcance (no-objetivos)
- **Desplegar de verdad el stack en la VPS B**: los ficheros de infraestructura (`docker-compose`,
  reglas de Prometheus/Alertmanager, dashboard de Grafana) se dejan completos y versionados, pero
  desplegarlos y verificarlos contra la VPS real de producción/staging queda pendiente de una sesión
  futura con acceso a esa infraestructura — mismo patrón ya usado en S4.6 (Caddy/TLS real) y S2.2
  (verificación en hardware real).
- **Canal real de alertas (email/Slack/etc.)**: Alertmanager se deja configurado con un receptor de
  ejemplo documentado (sin credenciales reales, sin enviar nada) — el canal real de aviso (a qué
  correo o Slack llega la alerta) es una decisión de Julio pendiente de tomar cuando se despliegue.
- **Alerta de expiración de certificados TLS**: requiere una sonda contra un dominio público real con
  TLS (Caddy on-demand TLS, S4.6), que todavía no existe en ningún entorno accesible desde aquí. Se
  deja documentada como regla pendiente de añadir cuando exista ese dominio real, no se inventa contra
  nada.
- **Alerta de disco**: la regla de Prometheus se escribe contra las métricas de `node-exporter`
  (estándar), pero `node-exporter` en sí mismo mide la VPS real — sin esa VPS desplegada, la regla
  existe pero no se puede verificar de extremo a extremo en este entorno.
- **Activar de verdad Sentry**: Julio aún no tiene cuenta; el SDK queda integrado y apagado (§0).
- **Dashboards elaborados de Grafana**: un dashboard básico (peticiones HTTP, tasa de 5xx, profundidad
  de cola OCR) es suficiente para esta tarea; iterar el diseño visual es trabajo futuro.

## 7. Notas de verificación (cómo se prueba de extremo a extremo)
- C1/C2: test de comportamiento inyectando/quitando `SENTRY_DSN` del entorno antes de `create_app()`
  (mismo patrón que el fixture `prod_client` de `test_security_headers.py`), con un doble
  (monkeypatch) del punto de entrada `sentry_sdk.init` para no llamar a una red real.
- C3-C6: cliente HTTP real (`httpx.AsyncClient` vía ASGI) contra `GET /metrics`, con Redis real de
  test; los trabajos se encolan con el mismo mecanismo real que usa la API
  (`arq.create_pool(...).enqueue_job(..., _queue_name=...)`), nunca simulados a mano.
- Infraestructura (docker-compose, reglas de Prometheus/Alertmanager, provisioning de Grafana): se
  verifica que los ficheros son sintácticamente válidos (`docker compose config`, YAML válido) y que
  las reglas de Prometheus pasan `promtool check rules` si está disponible en este entorno; el
  comportamiento real de alerta (dispara/no dispara) queda pendiente del despliegue real (§6).
