# Spec: S6.9 Captura de cámara fiable desde la pantalla de factura

> Spec-Driven Domain. Esta spec es la fuente única que alimenta los tests y las auditorías. Si algo
> no está aquí, no se implementa.

- **ID / tarea:** S6.9
- **Contexto (módulo):** `frontend/features/capture`
- **ADR relacionados:** ADR-0002 (PWA primero y cámara web)
- **Estado:** implementada y verificada localmente (2026-08-13); pendiente de prueba manual Android/iPhone

## 1. Problema y valor de dominio

En dispositivos reales, pulsar "Tomar foto" no siempre lleva a la revisión. El flujo actual pide
siempre la cámara trasera al cargar y el botón solo puede capturar si el vídeo ya tiene píxeles; si
la cámara tarda, el navegador no acepta la restricción trasera o el stream queda listo sin metadatos,
el usuario se queda con un aviso sin una recuperación clara. Subir una factura desde el móvil es el
camino principal del rol `user`, por lo que la captura manual debe funcionar o explicar de forma
accionable cómo continuar.

## 2. Lenguaje ubicuo

- **Cámara preparada:** stream concedido y vídeo con dimensiones de frame distintas de cero, listo
  para obtener una foto.
- **Cámara solicitada:** el navegador está esperando permiso o negociando un dispositivo.
- **Reintentar cámara:** acción explícita que libera un intento anterior y solicita de nuevo una
  cámara compatible.
- **Cámara compatible:** primero se intenta la trasera; si el dispositivo no puede ofrecerla, se
  acepta otra cámara de vídeo en vez de bloquear el flujo.
- **Fallback de archivo:** selector de archivo nativo, disponible siempre, que sigue llevando a la
  revisión obligatoria antes de subir.

## 3. Comportamientos (criterios de aceptación)

### C1 - La cámara trasera se prefiere sin bloquear dispositivos compatibles solo con otra cámara
- **Given** un navegador seguro con permiso de cámara concedido, pero sin cámara que cumpla la
  preferencia trasera.
- **When** entra en `/capturar` o reintenta la cámara.
- **Then** la app solicita una cámara de vídeo compatible sin exigir orientación trasera y muestra la
  vista previa si el navegador la concede.

### C2 - El botón solo se habilita cuando hay un frame capturable
- **Given** el stream está concedido pero el vídeo aún no tiene dimensiones.
- **When** el usuario ve la pantalla de captura.
- **Then** "Tomar foto" se muestra deshabilitado con el texto "Preparando cámara…"; no produce un
  aviso de error por pulsar demasiado pronto.

### C3 - La cámara preparada captura y llega a revisión
- **Given** la vista previa tiene un frame real.
- **When** el usuario pulsa "Tomar foto".
- **Then** captura ese frame, lo procesa y muestra la revisión obligatoria con "Repetir" y "Usar esta
  foto", igual que el flujo de S2.2.

### C4 - Si la cámara tarda o falla, el usuario puede reintentarlo
- **Given** el permiso fue denegado, la cámara se desconectó, el navegador falló o no hay soporte.
- **When** la app no puede mostrar una vista previa utilizable.
- **Then** explica el problema sin revelar detalles técnicos, mantiene "Subir archivo" disponible y
  muestra "Reintentar cámara" cuando el navegador soporta `getUserMedia`.

### C5 - Reintentar no deja streams anteriores activos
- **Given** hubo un intento de cámara anterior, activo o fallido.
- **When** el usuario pulsa "Reintentar cámara".
- **Then** el stream anterior se detiene antes de pedir otro y solo una vista previa queda activa.

### C6 - La recuperación no salta la revisión ni altera la subida
- **Given** una foto obtenida por cámara trasera, otra cámara o selector de archivo.
- **When** llega a la revisión y se sube.
- **Then** conserva normalización JPEG, selector Recibida/Emitida, empresa según rol, control antivirus
  y navegación a confirmación existentes.

### C7 - El navegador informa que la cámara está ocupada o sin permiso
- **Given** `getUserMedia` rechaza porque otra aplicación usa la cámara o el permiso está denegado.
- **When** la solicitud termina.
- **Then** la app no queda en "Pidiendo acceso" indefinidamente y ofrece inmediatamente el fallback
  de archivo y el reintento permitido por el navegador.

## 4. Invariantes y reglas de negocio

- Nunca se captura ni se procesa un frame vacío.
- Nunca queda más de un stream de cámara activo por pantalla de captura.
- La cámara trasera es una preferencia de experiencia móvil, no un requisito que impida usar una
  cámara disponible.
- El fallback de archivo sigue estando disponible con independencia del estado de cámara.
- Ninguna foto se sube sin revisión humana previa.

## 5. Casos límite y errores

- Contexto no seguro: se muestra fallback y explicación de que la cámara requiere conexión segura;
  no se ofrece un reintento inútil.
- Cambio de cámara/permiso en el sistema operativo: el stream terminado pasa al mismo estado de
  recuperación de C4.
- Doble pulsación de reintento: se ignora mientras existe una solicitud activa.
- Escritorio: se permite webcam si es la única cámara disponible, sin cambiar el diseño móvil.

## 6. Fuera de alcance

- Selector manual de cámara entre varias lentes.
- OCR o subida automática sin revisión.
- Recorte manual de esquinas.
- Cambios de backend, de `POST /uploads` o de permisos del sistema operativo.

## 7. Notas de verificación

- Frontend: tests de estados solicitando/preparada/fallida, fallback de orientación trasera, frame no
  listo, reintento, liberación de tracks y captura hasta revisión.
- Manual obligatorio: probar en Android y en iPhone reales, con permiso concedido, denegado y una
  segunda apertura de cámara después de volver a la aplicación.
